# 종목 캔들 조회 신뢰성 개선 Plan

## 기준 문서

- Overview: `docs/tasks/stock-candle-reliability/01-overview.md`
- Issue: [#9](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/9)

## 검증 가능한 완료 조건

1. KIS 호출 실패와 비정상 빈 응답이 신규 `isMissing=true` 행을 만들지 않는다.
2. 기존 실제 캔들이 있으면 KIS 장애 또는 락 경합 중에도 해당 데이터를 반환한다.
3. 반환 가능한 실제 캔들이 없고 KIS 조회가 실패하면 안정적인 오류 코드와 HTTP 503을 반환한다.
4. 캔들 조회 경로에서 새로 추가하거나 변경한 오류가 mapper 누락으로 HTTP 500이 되지 않는다.
5. 분봉 결측 후보는 거래일의 09:00~15:30 KST로 제한되고, 확인된 휴장일은 제외된다.
6. 기존 `isMissing=true` 행은 정상 데이터의 재조회를 막지 않는다.
7. 정상, 부분 성공, 빈 응답, KIS 실패, 락 획득 실패, 휴장일 달력 UNKNOWN을 테스트한다.
8. `MINUTE`, `DAY`, `WEEK` API 계약과 기존 배열 응답 형식을 유지한다.
9. 관련 테스트와 전체 `./gradlew test`가 통과한다.
10. 백엔드 운영 상태가 정상화된 뒤 실서비스 API에서 500 비노출과 캔들 응답을 확인한다.

## 구현 단계와 검증 방법

### 1. 외부 캔들 조회 결과를 명시적으로 표현

- `RealMarketClient`의 캔들 조회 결과에 캔들 목록과 완료 상태를 함께 표현하는 market 모듈 계약 타입을 도입한다.
- KIS adapter는 정상 완료, 일부 호출 실패, 전체 실패와 정상 빈 결과를 구분한다.
- 분봉의 내부 재시도 소진 시 `null`로 숨기지 않고 실패 상태를 상위 계층에 전달한다.

검증:

- adapter 단위 테스트에서 완료·부분·실패 결과와 실제 캔들 목록을 검증한다.
- 예외 또는 circuit breaker fallback이 일반 빈 목록으로 변환되지 않는지 검증한다.

### 2. 캐시 우선 fallback과 오류 계약 적용

- DB의 실제 캔들과 결측 행을 분리해 읽고, 실제 캔들은 외부 장애 시 fallback으로 사용한다.
- 외부 조회가 실패하거나 분산 락을 얻지 못했을 때 실제 캐시가 있으면 반환한다.
- 반환 가능한 캔들이 없을 때만 `DomainException`과 market 오류 코드를 발생시킨다.
- `MarketErrorHttpMapper`에서 해당 오류를 HTTP 503으로 명시적으로 매핑한다.

검증:

- application 테스트에서 캐시 있음/없음, KIS 실패, 락 획득 실패 조합을 검증한다.
- mapper 테스트와 API 테스트에서 `status`, `code`, `message`를 확인하고 500 fallback이 없음을 검증한다.

### 3. 거래 가능 슬롯만 계산

- 분봉 예상 시각을 KST 장 운영 시간으로 제한한다.
- 저장된 거래일 달력에서 확인된 주말·휴장일을 제외한다.
- 달력을 확인할 수 없는 날짜의 fallback 동작은 D4 결정에 따른다.
- 일봉 이상은 KIS 결과의 기간 정규화와 내부 `Timeframe` 경계를 일치시켜 중복과 누락을 방지한다.

검증:

- 평일 장중, 장외, 주말, 휴장일, 달력 UNKNOWN의 예상 슬롯을 단위 테스트한다.
- 주봉 원본 날짜가 내부 주 시작일로 한 번만 정규화되는지 검증한다.

### 4. 결측 영구 캐시 중단과 기존 데이터 복구

- 신규 캔들 조회에서는 제공자 응답에 없는 슬롯을 `isMissing=true`로 영구 저장하지 않는다.
- 기존 결측 행이 coverage로 인정되지 않게 해 실제 캔들 재조회를 허용한다.
- 기존 결측 행의 물리적 정리 방법은 D3 결정에 따라 구현 또는 운영 문서로 제공한다.

검증:

- 기존 결측 행만 있는 구간이 KIS 재조회 대상이 되는지 검증한다.
- KIS 실패 뒤 결측 행이 추가되지 않는지 repository interaction과 저장 상태로 검증한다.
- 실제 캔들의 유니크 키 중복 저장이 발생하지 않는지 검증한다.

### 5. 관측 가능성 추가

- 캔들 조회의 provider 실패, 부분 성공, 캐시 fallback, 503, 락 fallback을 구분하는 카운터를 추가한다.
- 로그에는 `stockId`, `timeframe`, 요청 범위와 결과 상태를 남기되 외부 자격 증명이나 전체 응답은 기록하지 않는다.

검증:

- 주요 application 테스트에서 필요한 meter 증가를 검증한다.
- 로그 인자에 민감 정보가 포함되지 않는지 코드 리뷰한다.

### 6. 전체 검증과 운영 재확인

- 작은 단위 테스트부터 실행하고 전체 테스트로 확장한다.
- 실서비스 백엔드가 정상화되면 종목 4971의 분봉·일봉·주봉을 직접 호출한다.
- HTTP status, 응답 건수, 시간 오름차순, OHLC 유효성, 응답 시간을 확인한다.

검증 명령:

```bash
./gradlew test --tests "depth.finvibe.modules.market.application.MarketQueryServiceCandleTest"
./gradlew test --tests "depth.finvibe.modules.market.infra.error.MarketErrorHttpMapperTest"
./gradlew compileJava
./gradlew test
```

## 사용자 결정 포인트

결정은 Plan 승인 후 D1부터 한 번에 하나씩 확정하고 `03-decisions.md`에 기록한다.

### D1. KIS 전체 실패 또는 비정상 빈 응답 정책

1. 실제 캐시가 있으면 캐시를 반환하고, 없으면 명시적 503을 반환한다.
   - 장점: 부분 장애가 전체 장애처럼 보이지 않고 빈 성공 응답이나 일반 500도 방지한다.
   - 단점: 캐시의 최신성이 요청 구간보다 낮을 수 있다.
2. 캐시 유무와 무관하게 항상 503을 반환한다.
   - 장점: 데이터 완전성 계약이 단순하다.
   - 단점: 쓸 수 있는 과거 데이터가 있어도 차트 전체가 실패한다.
3. 실패를 빈 배열로 반환한다.
   - 장점: 기존 프론트 처리는 단순하다.
   - 단점: 실제 데이터 없음과 장애를 구분할 수 없고 현재 문제를 반복한다.

AI 추천: 1번. 사용자가 사전 동의했으며 부분 장애를 격리하고 500을 제거하는 목표에 가장 잘 맞는다.

### D2. KIS 일부 호출만 성공한 경우의 응답

1. 성공한 실제 캔들을 저장하고 기존 캐시와 병합해 반환하며 부분 성공 메트릭을 남긴다.
   - 장점: 기존 배열 계약을 유지하면서 가능한 차트를 제공한다.
   - 단점: 응답만으로 완전한 구간인지 알 수 없다.
2. 새 부분 결과는 저장하되 응답에는 기존 캐시만 반환한다.
   - 장점: 사용자에게 갑자기 불연속 데이터가 보일 가능성을 줄인다.
   - 단점: 기존 캐시가 없으면 쓸 수 있는 새 데이터가 있어도 503이 된다.
3. 일부 실패가 하나라도 있으면 모든 결과를 버리고 503을 반환한다.
   - 장점: 엄격한 완전성 보장이 쉽다.
   - 단점: 부분 장애가 전체 차트 장애로 확대된다.

AI 추천: 1번. 사용자에게 표시 가능한 실제 데이터를 최대한 제공하고 부분 장애를 전체 장애로 확대하지 않는다.

### D3. 기존 `isMissing=true` 행 처리

1. 즉시 coverage에서 제외하고, 물리 삭제는 운영용 분할 삭제 SQL과 절차로 제공한다.
   - 장점: 배포 즉시 재조회가 가능하고 애플리케이션 시작 및 DB 부하 위험이 낮다.
   - 단점: 운영자가 정리하기 전까지 불필요한 행이 남는다.
2. 애플리케이션 시작 시 모든 결측 행을 자동 삭제한다.
   - 장점: 별도 운영 작업 없이 테이블을 정리한다.
   - 단점: 데이터량이 많으면 시작 지연, 대형 트랜잭션과 락 경합이 발생할 수 있다.
3. 스키마에 만료 시각을 추가하고 기존 행을 점진적으로 재검증한다.
   - 장점: 장기적으로 음수 캐시를 정교하게 운영할 수 있다.
   - 단점: 이번 버그 수정에 비해 스키마와 정책 복잡도가 크다.

AI 추천: 1번. 동작 복구와 물리 정리를 분리해 운영 위험을 최소화한다.

### D4. 휴장일 달력을 확인할 수 없는 날짜의 분봉 조회

1. 평일과 장 운영 시간만 적용해 KIS 조회를 계속하되 결측을 저장하지 않는다.
   - 장점: 달력 부분 장애가 실제 거래일 차트를 막지 않는다.
   - 단점: 실제 휴장일에도 KIS를 호출할 수 있다.
2. 달력 UNKNOWN이면 즉시 503을 반환한다.
   - 장점: 불확실한 조건에서 불필요한 외부 호출을 막는다.
   - 단점: 달력 장애가 차트 전체 장애로 전파된다.
3. 달력 UNKNOWN을 휴장일로 간주해 조회를 건너뛴다.
   - 장점: fail-closed 동작이 단순하다.
   - 단점: 실제 거래일 데이터를 빈 차트로 숨길 수 있다.

AI 추천: 1번. 영구 결측을 저장하지 않으므로 잘못된 음수 캐시 위험 없이 가용성을 우선할 수 있다.

### D5. 503 오류 코드의 식별자

1. market 전용 `MARKET_CANDLE_TEMPORARILY_UNAVAILABLE`을 추가한다.
   - 장점: 캔들 장애를 다른 현재가 부재나 일반 circuit breaker와 구분해 관측하고 대응할 수 있다.
   - 단점: 외부 오류 코드가 하나 추가된다.
2. 기존 `MARKET_NO_PRICE_DATA_AVAILABLE`을 재사용한다.
   - 장점: 새 계약이 없다.
   - 단점: 현재가 부재와 캔들 제공자 장애의 원인이 섞인다.
3. 전역 `CIRCUIT_BREAKER_OPEN`을 재사용한다.
   - 장점: 기존 503 매핑을 그대로 쓴다.
   - 단점: KIS 빈 응답, 락 경합과 circuit breaker를 구분하지 못한다.

AI 추천: 1번. 사용자에게는 동일한 503이어도 운영 원인 식별이 가능해야 한다.

## 의존 관계와 적용 순서

1. D1과 D2로 외부 조회 결과 및 fallback 계약을 확정한다.
2. D3으로 기존 결측 데이터의 논리·물리 복구 범위를 확정한다.
3. D4로 거래일 달력 장애 시 조회 정책을 확정한다.
4. D5로 API 오류 식별자를 확정한다.
5. 결정별로 계약 타입 → application 흐름 → persistence → 오류 mapper → 관측 코드 순서로 구현한다.
6. 각 결정 구현 후 관련 테스트를 실행하고 독립 커밋을 만든다.
7. 전체 테스트와 운영 API 재검증 뒤 `04-result.md`와 PR을 작성한다.
