# 종목 캔들 조회 신뢰성 개선 Decisions

## 결정 상태

- 사용자가 2026-08-21 D1~D6과 D8은 A, D7은 B로 명시적으로 선택했다.

## D1. KIS 전체 실패 또는 비정상 빈 응답 정책

### 검토한 선택지

- A: 실제 캐시가 있으면 캐시를 반환하고, 없으면 명시적 503을 반환한다.
- B: 캐시 유무와 무관하게 항상 503을 반환한다.
- C: 실패를 빈 배열로 반환한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-21

### 선택 이유

- KIS 장애를 차트 전체 장애로 확대하지 않고 이미 확보된 실제 캔들을 제공한다.
- 정상적인 데이터 없음과 외부 장애를 빈 배열로 숨기지 않는다.
- 반환 가능한 데이터가 없을 때 의도된 503으로 구분해 일반 500 노출을 방지한다.

### 감수한 트레이드오프

- fallback 캐시가 요청 범위 전체를 포함하지 않거나 최신성이 낮을 수 있다.
- 기존 배열 응답만으로 fallback 여부를 알 수 없어 로그와 메트릭이 필요하다.

## D2. KIS 일부 호출만 성공한 경우의 응답

### 검토한 선택지

- A: 성공한 실제 캔들을 저장하고 기존 캐시와 병합해 반환하며 부분 성공 메트릭을 남긴다.
- B: 새 부분 결과는 저장하되 응답에는 기존 캐시만 반환한다.
- C: 일부 실패가 하나라도 있으면 모든 결과를 버리고 503을 반환한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-21

### 선택 이유

- 유효한 실제 데이터를 최대한 제공해 일부 KIS 호출 실패를 전체 차트 장애로 확대하지 않는다.
- 기존 배열 API 계약을 바꾸지 않고도 차트 가용성을 높일 수 있다.
- 부분 성공은 별도 메트릭과 로그로 운영자가 식별한다.

### 감수한 트레이드오프

- 클라이언트는 응답 배열만으로 요청 구간이 완전한지 알 수 없다.
- 부분 데이터 사이에 시간 간격이 생길 수 있다.

## D3. 기존 `isMissing=true` 행 처리

### 검토한 선택지

- A: 즉시 coverage에서 제외하고 물리 삭제는 운영용 분할 삭제 SQL과 절차로 제공한다.
- B: 애플리케이션 시작 시 모든 결측 행을 자동 삭제한다.
- C: 스키마에 만료 시각을 추가하고 기존 행을 점진적으로 재검증한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-21

### 선택 이유

- 배포 직후 기존 결측 행이 정상 데이터 재조회를 막지 않게 한다.
- 대량 삭제를 애플리케이션 시작 경로에서 분리해 시작 지연과 DB 락 위험을 피한다.
- 물리 삭제는 운영자가 데이터량과 부하를 확인하며 작은 단위로 수행할 수 있다.

### 감수한 트레이드오프

- 운영 정리를 수행하기 전까지 불필요한 결측 행이 DB에 남는다.
- 분할 삭제 절차를 별도로 실행하고 완료 여부를 확인해야 한다.

## D4. 휴장일 달력을 확인할 수 없는 날짜의 분봉 조회

### 검토한 선택지

- A: 평일과 장 운영 시간만 적용해 KIS 조회를 계속하되 결측을 저장하지 않는다.
- B: 달력 UNKNOWN이면 즉시 503을 반환한다.
- C: 달력 UNKNOWN을 휴장일로 간주해 조회를 건너뛴다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-21

### 선택 이유

- 달력 부분 장애가 실제 거래일 차트 조회를 막지 않는다.
- 결측 영구 저장을 중단하므로 휴장일을 평일로 fallback해도 잘못된 음수 캐시가 남지 않는다.
- 확인된 휴장일은 제외하면서 UNKNOWN에만 가용성 우선 fallback을 적용한다.

### 감수한 트레이드오프

- 실제 휴장일의 달력 상태가 UNKNOWN이면 불필요한 KIS 호출이 발생할 수 있다.
- 달력 UNKNOWN 횟수를 메트릭으로 관찰해야 한다.

## D5. 503 오류 코드의 식별자

### 검토한 선택지

- A: market 전용 `MARKET_CANDLE_TEMPORARILY_UNAVAILABLE`을 추가한다.
- B: 기존 `MARKET_NO_PRICE_DATA_AVAILABLE`을 재사용한다.
- C: 전역 `CIRCUIT_BREAKER_OPEN`을 재사용한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-21

### 선택 이유

- 캔들 제공자 장애와 현재가 부재, 일반 circuit breaker를 안정적인 오류 코드로 구분한다.
- 오류 mapper에 명시적으로 등록해 예상하지 못한 500 fallback을 방지한다.
- 운영 메트릭과 로그에서 캔들 가용성 문제를 독립적으로 추적할 수 있다.

### 감수한 트레이드오프

- 외부 오류 계약에 새로운 code가 추가된다.
- 기존 클라이언트가 503의 세부 code를 분기하려면 후속 대응이 필요할 수 있다.

## D6. 실데이터 분봉 생성·복구 방식

### 검토한 선택지

- A: KIS REST를 누락 복구 경로로 유지하고 WebSocket 구독 종목의 체결을 분봉으로 집계·저장한다.
- B: KIS REST 요청 기반 적재만 사용한다.
- C: WebSocket 집계만 사용한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-21

### 선택 이유

- WebSocket 구독 종목은 장중 분봉을 지속적으로 적재한다.
- 재시작, 미구독과 수신 누락 구간은 KIS REST 조회가 복구한다.
- 제한된 WebSocket 세션 용량 때문에 구독되지 않은 임의 종목도 차트 요청 시 복구할 수 있다.
- 별도 Batch 작업 없이 기존 조회 경로와 실시간 이벤트 경로를 결합한다.

### 감수한 트레이드오프

- WebSocket 집계와 REST 복구가 같은 분봉을 동시에 저장할 수 있으므로 멱등 upsert가 필요하다.
- 처리 중인 현재 분은 체결이 들어올 때마다 값이 변하며, 완료된 분과 구분해 관측해야 한다.
- WebSocket 미구독 종목은 조회 요청 전까지 DB에 분봉이 없을 수 있다.

## D7. 과거 mock 오염 데이터 식별·삭제 방식

### 검토한 선택지

- A: 기존 mock 생성식과 모든 값이 일치하는 행만 선별해 삭제한다.
- B: 종목 캔들 전체를 삭제하고 KIS REST 조회로 다시 채운다.
- C: mock 운영 기간에 해당하는 캔들 시각만 삭제한다.

### 결정

- 선택: B
- 결정자: 사용자
- 결정일: 2026-08-21

### 선택 이유

- `price_candle`에 생성 시각과 데이터 출처가 없어 오염 행을 완전하게 식별할 수 없다.
- mock은 요청받은 과거 구간까지 생성했으므로 운영 기간이나 캔들 시각만으로 삭제하면 오염이 남는다.
- 일부 오염을 남기는 것보다 전체 종목 캔들을 비우고 실데이터로 다시 구성하는 방향을 선택했다.

### 감수한 트레이드오프

- KIS 호출량과 재조회 시간이 증가한다.
- KIS가 더 이상 제공하지 않는 오래된 분봉은 복구하지 못할 수 있다.
- 복구 전까지 차트 데이터가 일시적으로 비거나 부분적으로 보일 수 있다.
- 실제 삭제 전 백업, 대상 건수 dry-run, 분할 삭제와 사후 검증이 필요하며 사용자 확인 없이 실행하지 않는다.

## D8. WebSocket 체결의 분봉 OHLCV 집계 방식

### 검토한 선택지

- A: 개별 체결가와 `CNTG_VOL`을 기준으로 OHLCV를 집계한다.
- B: 당일 누적 거래량·거래대금의 이벤트 간 차이로 집계한다.
- C: 이벤트의 당일 OHLC와 누적 거래량·거래대금을 그대로 저장한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-21

### 선택 이유

- open은 해당 분의 첫 체결가, high와 low는 최고·최저 체결가, close는 마지막 체결가로 계산한다.
- volume은 개별 `CNTG_VOL`의 합, value는 각 `체결가 × 체결량`의 합으로 계산해 분봉 의미를 유지한다.
- KIS 이벤트의 OHLC와 누적 거래량·거래대금은 당일 기준이므로 분봉에 직접 쓰지 않는다.
- WebSocket 메시지 누락은 이미 선택한 KIS REST 복구 경로가 보완한다.

### 감수한 트레이드오프

- 메시지가 유실되면 REST 복구 전까지 해당 분의 OHLCV가 불완전할 수 있다.
- 재접속 뒤 같은 분의 기존 DB 캔들과 새 체결을 병합할 때 첫 체결 순서를 보존해야 한다.
