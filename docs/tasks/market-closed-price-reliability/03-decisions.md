# 장외 시세와 휴장일 판정 신뢰성 개선 Decisions

## D1. 기존 종가 API의 부분 실패 계약

- 상태: 확정
- 결정: **B — 기존 endpoint를 유지하고 부분 응답을 명시하는 v2 endpoint를 추가한다.**
- 확정일: 2026-08-21

### 적용 방식

- 기존 `/market/stocks/closing-prices`의 배열 응답은 유지한다.
- v2 응답은 `items`, `missingStockIds`, `partial`, `tradingDate`, `asOf`를 제공한다.
- 기존 endpoint의 부분 누락 동작은 하위 호환을 위해 유지하되, 누락 건수와 외부 배치 실패를 로그·지표로 기록한다.
- 새 소비자는 v2 응답으로 정상 전체 결과와 부분 장애를 구분할 수 있다.

### 결정 이유

- 일부 외부 시세 배치 실패를 전체 API 장애로 확대하지 않는다.
- 기존 프론트엔드 응답 형식을 깨지 않는다.
- 단순 부분 배열만 반환하는 방식과 달리 신규 소비자에게 누락 정보를 제공한다.

## D2. 휴장일 달력 확인 실패 정책

- 상태: 확정
- 결정: **A — 저장된 달력 정보가 없고 외부 동기화도 실패하면 `CLOSED`로 판정한다.**
- 확정일: 2026-08-21

### 적용 방식

- 먼저 저장된 거래일 달력을 조회한다.
- 필요한 날짜 정보가 없으면 KIS 달력 동기화를 시도한다.
- 동기화 후에도 판정할 수 없으면 `OPEN`으로 추정하지 않고 `CLOSED`를 반환한다.
- 달력 동기화 실패와 fail-closed 판정 횟수를 로그·지표로 기록한다.

### 결정 이유

- 실제 휴장일을 개장일로 잘못 판정해 장중 시세 경로를 노출하는 위험을 막는다.
- 정상 운영에서는 미리 저장된 달력을 사용하므로 외부 API의 일시 장애가 즉시 시장 상태 장애로 번지지 않는다.

## D3. 시장 상태 응답 메타데이터

- 상태: 확정
- 결정: **A — 기존 `status`를 유지하고 `reason`, `tradingDate`, `asOf`를 추가한다.**
- 확정일: 2026-08-21

### 적용 방식

- `status` 값은 기존 `OPEN/CLOSED`를 유지한다.
- `reason`에는 거래일 장중, 장외 시간, 주말, 휴장일, 달력 확인 실패 등 판정 근거를 제공한다.
- `tradingDate`에는 상태 판정에 사용한 거래 기준일을 제공한다.
- `asOf`에는 서버가 상태를 판정한 한국 시간 기준 시각을 제공한다.
- 신규 필드는 기존 소비자가 무시할 수 있는 하위 호환 필드로 추가한다.

### 결정 이유

- 기존 프론트엔드의 `status` 분기를 깨지 않는다.
- 휴장일과 달력 장애를 단순 `CLOSED`와 구분해 진단할 수 있다.

## D4. 종가 사전 적재 범위와 시각

- 상태: 확정
- 결정: **A — 전체 등록 종목을 평일 15:40 KST에 적재하고 불완전할 때만 복구 실행한다.**
- 확정일: 2026-08-21

### 적용 방식

- 휴장일이 아닌 평일 장 마감 후 전체 등록 종목을 대상으로 실행한다.
- KIS 멀티종목 제한에 맞춰 30종목 단위로 분할한다.
- 기존 호출 제한 제어를 재사용하고 실패 배치에는 제한된 재시도를 적용한다.
- 서버 지연 기동 또는 정규 실행 실패 시 최근 거래일 데이터가 불완전한 경우에만 복구 실행한다.
- 일부 종목이 끝내 실패하면 성공으로 숨기지 않고 실패 수와 대상을 로그·지표에 남긴다.

### 결정 이유

- 종목 탐색과 모의투자는 보유 여부와 무관한 종목을 조회하므로 전체 종목을 준비해야 콜드 요청을 제거할 수 있다.
- 조건부 복구로 정상 상태에서 불필요한 외부 API 재호출을 방지한다.

## D5. 종가 보존 기간

- 상태: 확정
- 결정: **A — 달력 기준 최근 30일 데이터를 보존하고 그 이전 데이터만 삭제한다.**
- 확정일: 2026-08-21

### 적용 방식

- 장 시작 시 `closing_price` 전체 삭제 작업을 제거한다.
- 정리 실행일로부터 30일 이전의 종가만 일괄 삭제한다.
- 최근 거래일 종가는 장 시작과 애플리케이션 재시작 이후에도 유지한다.

### 결정 이유

- 휴장일, 외부 API 장애와 재시작 시 직전 거래일 데이터를 재사용할 수 있다.
- 무기한 누적으로 인한 저장 공간 증가를 제한한다.

## D6. Monolith와 Batch 전달 방식

- 상태: 확정
- 결정: **A — 저장소별 연결 Issue, Issue 번호 브랜치와 PR을 만들어 함께 전달한다.**
- 확정일: 2026-08-21

### 적용 방식

- Monolith는 Issue #7과 현재 작업 브랜치에서 API, 휴장일 판정, 조회·보존 정책을 변경한다.
- Batch에는 Monolith #7을 연결한 별도 Issue를 만들고 해당 번호를 포함한 브랜치에서 워밍업을 구현한다.
- 두 PR의 설명에 상대 Issue·PR과 함께 배포해야 하는 이유를 명시한다.
- 승인과 병합은 사용자가 수행한다.

### 결정 이유

- 조회 계약과 사전 적재 중 한쪽만 적용했을 때 남는 콜드 패스와 부분 장애 식별 문제를 함께 해결한다.
- 저장소별 변경 이력과 롤백 단위를 분리한다.
