# 장외 시세와 휴장일 판정 신뢰성 개선 Plan

Overview와 GitHub Issue [#7](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/7)을 기준으로 구현 순서와 결정 포인트를 정의한다. 무중단 배포, 프론트엔드, 뉴스, 스쿼드 기능은 이 작업에서 다루지 않는다.

## 목표 산출물

- Monolith
  - 휴장일 달력을 반영하는 단일 시장 상태 판정 경로
  - 기존 응답 형식을 유지하는 장외 종가 조회의 완전성 검증
  - KIS 멀티종목 일부 배치 실패를 숨기지 않는 오류 계약
  - 최근 거래일 종가 보존 및 오래된 데이터 정리 정책
  - 단위·통합 테스트와 Micrometer 관측 지표
- Batch
  - 장 마감 후 전체 종목의 최근 거래일 종가를 미리 적재하는 전용 작업
  - 재시도 가능한 부분 실패 결과와 실행 지표
  - Monolith와 동일한 휴장일·종가 저장 규칙
- 문서
  - 결정 기록, 실제 변경 결과, 검증 및 운영 롤백 절차

## 완료 조건

- 평일 거래소 휴장일에는 시간대가 장중이어도 시장 상태가 `OPEN`이 아니다.
- 휴장일 달력의 저장 데이터와 외부 동기화가 모두 불가능하면 임의로 평일을 개장일로 간주하지 않는다.
- `/market/stocks/closing-prices`의 기존 JSON 배열 계약은 유지한다.
- 기존 endpoint는 배열 계약을 유지하고, v2 endpoint는 누락 종목과 부분 응답 여부를 명시한다.
- 장 마감 뒤 사용자 요청 이전에 전체 종목의 최근 거래일 종가를 적재할 수 있다.
- 종가 저장 데이터는 최근 30일만 유지하고 장 시작 시 전체 삭제하지 않는다.
- 외부 시세 부분 실패, 종가 누락, 달력 동기화 실패, 워밍업 결과를 로그와 지표로 확인할 수 있다.
- Monolith와 Batch의 관련 테스트가 통과한다.

## 구현 단계

### S1. 휴장일 기반 시장 상태 판정

- `MarketHours`는 순수한 장 운영 시간 판정만 담당한다.
- `HolidayCalendarService`에 특정 날짜의 거래 여부를 조회하는 기능을 추가한다.
- `MarketStatusService`가 한국 시간의 날짜·시각과 거래일 여부를 조합해 최종 `OPEN/CLOSED`를 계산한다.
- 시장 상태 응답의 기존 `status` 필드는 유지하고 판정 사유, 기준 거래일, 서버 기준 시각을 선택적으로 추가한다.
- 달력 동기화 실패 시 명확한 로그·카운터를 남기고 결정 D2의 정책을 적용한다.

검증:

- 정상 평일 장중, 장외, 주말, 평일 휴장일 테스트
- 달력 캐시 적중, 외부 동기화 성공, 외부 동기화 실패 테스트
- 기존 `status` 역직렬화 호환성 검토

### S2. 장외 종가 완전성 및 오류 계약

- 요청 ID 중 존재하지 않는 종목과 존재하지만 가격 확보에 실패한 종목을 구분한다.
- DB에서 최근 거래일 종가를 먼저 조회하고, 누락 종목만 KIS 보충 경로로 전달한다.
- KIS 30종목 배치 결과가 불완전하면 실패 심볼과 원인을 결과 타입으로 상위 계층에 전달한다.
- 정상 종목의 최종 종가 수가 요청 수와 다르면 v2 응답의 `missingStockIds`와 `partial`에 반영한다.
- 기존 `List<ClosingPriceDto.Response>` 응답과 각 항목의 `at` 필드는 유지하고 누락 건수는 로그·지표로 관측한다.

검증:

- 전체 DB 적중, 일부 DB 적중 후 KIS 보충, 전체 KIS 보충 테스트
- 한 개 KIS 배치 실패, KIS 빈 결과, 알 수 없는 종목 ID 테스트
- 기존 배열 응답 스키마 회귀 테스트

### S3. 종가 보존 및 정리 정책

- 장 시작 시 `closing_price` 전체를 삭제하는 스케줄을 제거한다.
- 최근 30일 이전 레코드만 일괄 삭제하는 저장소 연산을 추가한다.
- 동일 `(stock_id, trading_date)` 저장은 멱등적으로 처리한다.
- 조회 기준은 항상 `HolidayCalendarService`가 계산한 최근 거래일로 통일한다.

검증:

- 여러 거래일 데이터 공존, 동일 키 재저장, 30일 경계 삭제 테스트
- 장 시작 후에도 직전 거래일 종가가 남는지 검증

### S4. Batch 종가 워밍업

- Batch 저장소에 연결 Issue와 별도 Issue 번호 브랜치를 만든다.
- 평일 15:40 KST에 전체 등록 종목을 30개씩 나눠 최근 거래일 종가를 조회·저장한다.
- 외부 API 제한을 존중하도록 기존 KIS 호출 제어를 재사용하고, 실패 배치는 제한된 횟수만 재시도한다.
- 일부 배치가 실패하면 작업을 성공으로 위장하지 않고 실패 심볼 수와 재실행 가능 상태를 기록한다.
- 서버 시작 또는 스케줄 지연 시 최근 거래일 데이터가 불완전한 경우에만 복구 실행할 수 있는 application entry point를 둔다.
- 워밍업 뒤 30일 이전 종가를 정리한다.

검증:

- 전체 성공, 일부 실패 후 재시도 성공, 재시도 소진 테스트
- 휴장일·주말 스킵과 지연 기동 복구 테스트
- Monolith와 Batch의 종가 엔티티·저장 규칙 대조

### S5. 관측성 및 최종 검증

- 최소 지표:
  - 휴장일 달력 동기화 실패 횟수
  - 종가 요청 누락 종목 수와 KIS 보충 횟수
  - KIS 멀티종목 배치 실패 횟수
  - 워밍업 대상·성공·실패 종목 수와 마지막 성공 시각
- 오류 로그에는 거래일, 배치 크기, 실패 종목 수, 외부 오류 분류를 포함하고 토큰·인증 정보는 남기지 않는다.
- 전체 테스트와 변경 범위 정적 검토 후 각 저장소에 Result 문서를 작성한다.
- 두 저장소의 브랜치를 push하고 서로 연결된 PR을 생성한다. 승인과 병합은 사용자가 수행한다.

## 결정 포인트

### D1. 기존 종가 API의 부분 실패 계약

선택지:

- A. 기존 배열 응답은 유지하되 정상 종목 중 하나라도 종가가 없으면 전체 요청을 503으로 실패시킨다.
- B. 기존 endpoint는 그대로 두고 `items`, `missingStockIds`, `partial`을 담는 v2 endpoint를 추가한다.
- C. 현재처럼 확보한 종목만 배열로 반환하고 누락은 지표로만 기록한다.

확정: **B**. 일부 외부 시세 배치 실패를 전체 장애로 확대하지 않는다. 기존 프론트 응답 형식은 유지하고, 신규 소비자는 v2의 `missingStockIds`와 `partial`로 부분 장애를 구분한다.

### D2. 휴장일 달력 확인 실패 정책

선택지:

- A. DB에도 날짜 정보가 없고 외부 동기화도 실패하면 시장을 `CLOSED`로 판정하고 지표를 남긴다.
- B. 달력 확인 실패 시 기존처럼 평일과 시간만으로 `OPEN/CLOSED`를 판정한다.
- C. `UNKNOWN` 상태를 새로 추가해 반환한다.

AI 추천: **A**. 거래 여부가 불확실한 날에 실시간 시세 경로를 개장 상태로 노출하는 것보다 안전하며 기존 `OPEN/CLOSED` enum도 유지한다. 운영자는 지표를 통해 달력 장애를 복구한다.

### D3. 시장 상태 응답 메타데이터

선택지:

- A. 기존 `status`를 유지하면서 `reason`, `tradingDate`, `asOf`를 nullable 필드로 추가한다.
- B. 응답은 전혀 변경하지 않고 서버 내부 판정만 개선한다.
- C. `HOLIDAY`, `PRE_OPEN`, `AFTER_HOURS`를 status enum에 추가한다.

AI 추천: **A**. 기존 프론트는 `status`만 계속 사용할 수 있고, 장애 분석과 향후 UI 개선에 필요한 판정 근거를 하위 호환 방식으로 제공한다.

### D4. 종가 사전 적재 범위와 시각

선택지:

- A. 전체 등록 종목을 평일 15:40 KST에 적재하고, 불완전할 때만 지연 기동 복구를 허용한다.
- B. 보유 종목·카테고리 종목만 적재한다.
- C. 배치를 추가하지 않고 첫 사용자 요청의 lazy fetch만 개선한다.

AI 추천: **A**. 종목 탐색과 모의투자는 보유 여부와 무관한 종목을 조회하므로 전체 적재가 사용자 요청의 콜드 패스를 제거한다. 30개 분할, 호출 제한, 제한 재시도로 KIS 부하를 제어한다.

### D5. 종가 보존 기간

선택지:

- A. 최근 30일 데이터를 보존하고 그 이전만 삭제한다.
- B. 현재처럼 장 시작 시 전체 삭제한다.
- C. 기간 제한 없이 누적한다.

AI 추천: **A**. 휴장·장애·재시작 시 직전 거래일 데이터를 복구에 활용할 수 있고 저장 공간도 제한한다.

### D6. Monolith와 Batch 전달 방식

선택지:

- A. Monolith Issue #7과 Batch의 연결 Issue를 각각 만들고, 별도 브랜치·PR로 함께 전달한다.
- B. Monolith만 변경하고 Batch 워밍업은 다음 작업으로 미룬다.
- C. Batch만 변경하고 API 오류 및 휴장일 계약은 유지한다.

AI 추천: **A**. 워밍업과 조회 계약 중 한쪽만 바꾸면 콜드 패스 또는 부분 성공 문제가 남는다. 저장소별 변경 이력은 분리하되 동일 결정과 검증 기준으로 묶는다.
