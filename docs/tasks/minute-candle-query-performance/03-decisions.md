# 분봉 조회 성능 개선 Decisions

## 결정 상태

- D1~D3: A 확정
- D4~D5: 미확정

## D1. 당일 최근 완료 분봉의 REST 보정 범위

### 검토한 선택지

- A: 마지막 3개 완료 분봉을 보정한다.
- B: 마지막 1개 완료 분봉만 보정한다.
- C: 당일의 모든 완료 분봉을 보정한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-22

### 선택 이유

- 한 번의 KIS 분봉 호출 범위 안에서 최근 3개 완료 분봉을 함께 보정할 수 있다.
- KIS REST 반영 지연이나 직전 WebSocket 메시지 유실로 마지막 분만 불완전할 때 직전 구간까지 다시 확인한다.
- 당일 전체를 반복 조회하지 않아 장중 시간이 지날수록 호출 횟수가 증가하는 문제를 막는다.

### 감수한 트레이드오프

- 최근 3분은 정상 캐시가 있어도 보정 시점에는 다시 조회한다.
- 3분보다 오래된 WebSocket 내부 공백의 복구 여부는 D2의 coverage 결정에 따른다.

## D2. 거래일 내부에 비어 있는 분의 누락 판정

### 검토한 선택지

- A: 해당 거래일에 정상 분봉이 하나라도 있으면 내부의 빈 분은 무체결 가능성이 있는 것으로 보고 최근 보정 범위 밖에서는 재조회하지 않는다.
- B: 모든 빈 분을 실제 누락 후보로 보고 연속 구간별로 계속 재조회한다.
- C: KIS에서 정상 확인한 빈 분을 Redis에 만료형 coverage로 기록해 실제 미확인 공백만 재조회한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-22

### 선택 이유

- KIS가 반환하지 않는 무체결 분을 실제 장애로 오인해 같은 거래일 전체를 반복 조회하는 문제를 막는다.
- 기존 DB 데이터만으로 판정할 수 있어 새 스키마나 Redis coverage 정책 없이 성능 문제를 해결할 수 있다.
- 정상 분봉이 전혀 없는 거래일과 기존 `isMissing=true` 행만 있는 거래일은 계속 KIS 복구 대상으로 유지한다.

### 감수한 트레이드오프

- 정상 분봉이 일부라도 있는 거래일에서 최근 보정 범위보다 오래된 실제 WebSocket 수신 공백은 자동 복구하지 못할 수 있다.
- 분 단위의 정확한 무체결과 수신 누락 구분은 데이터 출처 또는 provider 검증 메타데이터를 도입하는 별도 작업이 필요하다.

## D3. 동일한 최근 구간의 재검증 빈도

### 검토한 선택지

- A: 종목별 마지막 완료 분마다 한 번만 KIS에서 검증하고 Redis에 검증 시각을 기록한다.
- B: 모든 차트 요청에서 최근 보정 범위를 KIS에 조회한다.
- C: 프로세스 메모리에 검증 시각을 기록한다.

### 결정

- 선택: A
- 결정자: 사용자
- 결정일: 2026-08-22

### 선택 이유

- 같은 종목의 반복 요청과 여러 애플리케이션 노드가 동일 완료 분을 중복 조회하지 않게 한다.
- KIS 호출이 완전히 성공한 경우에만 검증 상태를 기록해 실패 또는 부분 성공은 다음 요청에서 다시 확인한다.
- 기존 Redis 인프라를 사용하되 application은 output port만 의존해 저장 기술을 캡슐화한다.

### 감수한 트레이드오프

- Redis 조회와 쓰기가 분봉 요청 경로에 한 번씩 추가된다.
- Redis 장애 시 검증 상태를 재사용하지 못하고 KIS를 다시 호출할 수 있다.
- 검증 상태는 장기 데이터가 아니므로 TTL 만료 후 같은 완료 분을 다시 검증할 수 있다.
