# 분봉 조회 성능 개선 Plan

## 기준 문서

- Overview: `docs/tasks/minute-candle-query-performance/01-overview.md`
- Issue: [#13](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/13)

## 검증 가능한 완료 조건

1. 완료된 과거 거래일에 정상 분봉 캐시가 있으면 해당 거래일 전체를 KIS에서 다시 조회하지 않는다.
2. 캐시가 전혀 없는 거래일 또는 확정된 누락 판정 범위는 KIS에서 복구한다.
3. 당일 최근 완료 분봉은 확정된 범위와 빈도로 KIS REST 결과를 사용해 보정한다.
4. 캐시가 갖춰진 최근 3거래일 재조회에서 외부 호출 횟수가 확정된 상한을 넘지 않는다.
5. KIS 실패, 부분 성공과 분산 락 실패 시 기존 캐시 fallback 및 503 계약을 유지한다.
6. `DAY`, `WEEK`, `MONTH`, `YEAR`의 누락 계산과 provider 호출 동작은 바뀌지 않는다.
7. 관련 단위 테스트, `compileJava`와 전체 테스트가 통과한다.
8. 배포 후 운영 분봉 API에서 응답시간과 KIS 호출량을 확인한다.

## 구현 단계와 검증 방법

### 1. 분봉 coverage와 갱신 정책 분리

- 모든 기존 KIS 분봉을 coverage에서 제외하는 `requiresAuthoritativeMinuteRefresh` 조건을 제거한다.
- 과거 coverage, 실제 복구가 필요한 범위와 당일 최근 보정 범위를 별도로 계산한다.
- 일봉 이상 timeframe의 기존 계산은 유지한다.

검증:

- 완료된 과거 분봉 캐시만 있는 요청에서 provider를 호출하지 않는지 검증한다.
- 캐시가 없는 거래일은 provider 복구 범위에 포함되는지 검증한다.
- 기존 `isMissing=true` 행만으로는 정상 coverage가 생기지 않는지 검증한다.

### 2. 당일 최근 완료 분봉만 최종 보정

- 현재 진행 중인 분은 기존대로 REST 조회에서 제외한다.
- 최근 완료 분봉의 범위와 동일 구간 재검증 빈도는 D1과 D3 결정에 따른다.
- 검증 상태를 여러 노드에서 공유해야 하는 안을 선택하면 market application의 output port와 Redis adapter로 캡슐화한다.

검증:

- 고정된 `Clock`으로 진행 중인 분, 마지막 완료 분과 보정 범위 경계를 검증한다.
- 같은 완료 분에 대한 반복 요청의 provider 호출 횟수를 검증한다.
- 다음 분이 완료되면 새 보정 요청이 허용되는지 검증한다.

### 3. 누락 범위와 provider 호출 범위 최적화

- 거래일 내부의 빈 분을 실제 누락으로 판정할 기준은 D2 결정에 따른다.
- 서로 떨어진 복구 범위와 최근 보정 범위를 외부 client에 전달하는 방식은 D4 결정에 따른다.
- 요청하지 않은 중간 캐시 구간을 불필요하게 재조회하지 않는다.

검증:

- 무체결로 비어 있을 수 있는 분이 매 요청마다 거래일 전체 재조회를 유발하지 않는지 검증한다.
- 캐시가 없는 날짜와 최근 보정 범위가 떨어져 있을 때 확정된 호출 분할 정책을 검증한다.
- provider 일부 실패 시 성공 데이터 저장과 기존 캐시 병합을 유지하는지 검증한다.

### 4. 성능 회귀 검증과 운영 확인

- application 테스트에서 캐시 상태별 외부 호출 횟수와 시작·종료 시각을 검증한다.
- 성능 완료 기준은 D5 결정에 따른다.
- 배포 후 동일 종목과 최근 3거래일 범위를 최초 요청과 반복 요청으로 나눠 측정한다.

검증 명령:

```bash
./gradlew test --tests "depth.finvibe.modules.market.application.MarketQueryServiceCandleTest"
./gradlew compileJava
./gradlew test
```

## 사용자 결정 포인트

결정은 Plan 승인 후 D1부터 한 번에 하나씩 확정하고 `03-decisions.md`에 즉시 기록한다. Overview에서 승인한 "완료된 과거 분봉은 캐시를 사용하고 당일 최근 구간만 갱신" 원칙은 모든 선택지의 공통 전제다.

### D1. 당일 최근 완료 분봉의 REST 보정 범위

A. 마지막 3개 완료 분봉을 보정한다.
   - 장점: KIS 반영 지연과 직전 WebSocket 유실을 완충하면서 한 번의 REST 호출로 제한할 수 있다.
   - 단점: 요청할 때마다 최대 3분을 다시 받는다.
B. 마지막 1개 완료 분봉만 보정한다.
   - 장점: 호출 데이터 범위가 가장 작다.
   - 단점: KIS 반영이 늦거나 직전 분 보정이 실패하면 불완전 값이 남을 수 있다.
C. 당일의 모든 완료 분봉을 보정한다.
   - 장점: 장중 누락을 요청 시점마다 폭넓게 복구한다.
   - 단점: 시간이 지날수록 외부 호출이 늘어 현재 5초 이상 지연 문제가 재발한다.

AI 추천: A. 최근성 보정과 호출량 제한 사이의 균형이 가장 좋다.

### D2. 거래일 내부에 비어 있는 분의 누락 판정

A. 해당 거래일에 정상 분봉이 하나라도 있으면 내부의 빈 분은 무체결 가능성이 있는 것으로 보고, 최근 보정 범위 밖에서는 재조회하지 않는다.
   - 장점: KIS가 반환하지 않는 무체결 분 때문에 매번 거래일 전체를 재조회하는 문제를 막는다.
   - 단점: WebSocket이 장중 일부 구간만 유실한 경우 최근 범위 밖의 내부 공백을 자동 복구하지 못할 수 있다.
B. 모든 빈 분을 실제 누락 후보로 보고 연속 구간별로 계속 재조회한다.
   - 장점: 내부 수신 누락 복구 가능성이 가장 높다.
   - 단점: 무체결 분을 구분할 메타데이터가 없어 동일 구간을 영구적으로 반복 조회할 수 있다.
C. KIS에서 정상 확인한 빈 분을 Redis에 만료형 coverage로 기록해 실제 미확인 공백만 재조회한다.
   - 장점: 내부 누락 복구와 무체결 반복 조회를 함께 제어할 수 있다.
   - 단점: coverage port·Redis adapter·TTL 정책이 추가되어 구현과 운영 복잡도가 커진다.

AI 추천: A. 이번 성능 장애를 최소 변경으로 해결하며, 완전한 내부 공백 검증은 출처·검증 메타데이터를 갖춘 후 별도 작업으로 다루는 편이 안전하다.

### D3. 동일한 최근 구간의 재검증 빈도

A. 종목별 마지막 완료 분마다 한 번만 KIS에서 검증하고 Redis에 검증 시각을 기록한다.
   - 장점: 여러 노드와 반복 요청에서도 같은 분에 대한 중복 외부 호출을 막고 캐시 적중 응답을 빠르게 만든다.
   - 단점: Redis coverage port와 adapter가 추가된다.
B. 모든 차트 요청에서 최근 보정 범위를 KIS에 조회한다.
   - 장점: 구현이 단순하고 요청 시점의 최신 REST 값을 매번 받는다.
   - 단점: 반복 새로고침과 동시 사용자가 외부 호출량과 응답시간을 다시 증가시킨다.
C. 프로세스 메모리에 검증 시각을 기록한다.
   - 장점: 구현이 작고 Redis 호출이 없다.
   - 단점: 재시작과 다중 노드에서 상태가 공유되지 않아 중복 호출이 발생한다.

AI 추천: A. 현재 시스템이 Redis와 다중 노드 운영을 이미 사용하므로 중복 호출 제어가 일관된다.

### D4. 서로 떨어진 복구·보정 범위의 호출 방식

A. 연속된 범위별로 나눠 호출하고 결과 상태와 캔들을 병합한다.
   - 장점: 사이에 있는 정상 캐시 구간을 다시 조회하지 않는다.
   - 단점: application orchestration과 부분 성공 병합 로직이 늘어난다.
B. 가장 이른 시작부터 가장 늦은 종료까지 한 범위로 합쳐 한 번 호출한다.
   - 장점: application 호출 구조가 단순하다.
   - 단점: 외부 client 내부에서 날짜·2시간 단위 호출이 늘어나 성능 개선 효과가 줄어든다.
C. 요청당 가장 최근 범위 하나만 처리하고 과거 복구는 다음 요청으로 미룬다.
   - 장점: 한 요청의 외부 호출 상한이 가장 낮다.
   - 단점: 과거 데이터 복구가 요청 횟수에 의존하고 결과가 장기간 불완전할 수 있다.

AI 추천: A. 필요한 범위만 조회하면서 기존 부분 성공 정책을 유지할 수 있다.

### D5. 운영 성능 완료 기준

A. 캐시가 갖춰진 최근 3거래일 반복 조회의 서버 응답시간 1초 이내를 목표로 하고, 외부 호출은 동일 완료 분당 종목별 최대 1회로 검증한다.
   - 장점: 사용자 체감과 외부 호출량을 모두 검증할 수 있다.
   - 단점: 운영 네트워크 상태에 따라 응답시간이 일시적으로 초과할 수 있다.
B. 서버 응답시간 2초 이내를 목표로 하고 호출 횟수는 제한하지 않는다.
   - 장점: 달성 여유가 크다.
   - 단점: KIS 호출량 회귀를 성능 수치만으로 놓칠 수 있다.
C. 응답시간 목표 없이 단위 테스트의 외부 호출 횟수만 검증한다.
   - 장점: 환경 변화에 흔들리지 않는 검증이 가능하다.
   - 단점: 실제 5초 지연이 해결됐는지 완료 조건이 불명확하다.

AI 추천: A. 이번 작업의 사용자 증상과 구조적 원인을 함께 완료 조건으로 삼을 수 있다.

## 의존 관계와 적용 순서

1. D1로 최근 보정 시간 범위를 확정한다.
2. D2로 정상 캐시가 있는 거래일의 coverage 경계를 확정한다.
3. D3로 반복 요청과 다중 노드의 재검증 빈도를 확정한다.
4. D4로 복수 범위의 provider 호출·병합 방식을 확정한다.
5. D5로 자동 테스트와 운영 확인의 완료 기준을 확정한다.
6. 각 결정 직후 결정 문서, 구현, 관련 테스트와 독립 커밋을 완료한 뒤 다음 결정으로 이동한다.
7. 전체 검증과 운영 영향 정리 후 Result를 작성하고 PR을 생성한다.
