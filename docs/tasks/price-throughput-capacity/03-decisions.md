# 제한된 운영 자원에서 실시간 시세 처리량 한계 끌어올리기 Decisions

## D1. 단계별 측정 화면

- 결정일: 2026-09-26
- 검토한 선택지: 통합 대시보드 신규 / 기존 대시보드 + 문서 표 / 쿼리 결과만 문서에
- 선택: **Grafana에 "시세 처리량 부하 시험" 통합 대시보드를 새로 만들고, JSON을 Manifest 레포에 커밋** (사용자 선택)
- 이유: 단계별 전 구간을 한 화면에서 비교할 수 있고, 사용자가 직접 캡처해 포트폴리오 근거로 쓸 수 있다. JSON으로 재현할 수 있다.

## D2. 부하 발생 방식

- 결정일: 2026-09-26
- 검토한 선택지: mock 우선, 막히면 우회 추가 / mock만 / 처음부터 별도 발생 파드
- 선택: **모놀리식 mock으로 시작하고, 모놀리식이 병목이 된 뒤 뒤 단계 측정이 필요할 때만 별도 발생 파드를 추가** (사용자 선택)
- 이유: 실제 시세 진입점(버전 부여 포함)을 파이프라인에 그대로 두고 측정한다. 발생기 자체의 한계는 "목표 대비 실제 발행량"으로 구분한다.

## D3. 증량 단계·유지 시간·중단 기준

- 결정일: 2026-09-26
- 검토한 선택지: 세밀 단계 + 중단 기준 / 거친 단계 + 같은 기준 / 중단 기준 없이 끝까지
- 선택: **세밀 단계 + 중단 기준** (사용자 선택)

### 내용

- 단계(초당 건수): 100 → 250 → 500 → 1,000 → 2,500 → 5,000 → 10,000 → 20,000 → 37,000
- 유지 시간: 단계마다 5분
- 중단 기준(하나라도 해당하면 즉시 이전 단계로):
  - Redis 명령 지연 p99가 50ms를 넘는 상태가 1분 지속
  - 노드 CPU가 95%를 넘는 상태가 1분 지속
  - 파드 재시작 또는 OOM
  - 모놀리식 5xx 비율 1% 초과
- 모놀리식 재기동 없이 mock 설정을 바꾸는 방법을 S1에서 함께 검토한다(재기동마다 약 6분이 든다).

## D4. 자원 재배치 허용 범위

- 결정일: 2026-09-26
- 검토한 선택지: 노드 전체 안에서 자유 조정 / 한도 고정·코드 개선만 / 매번 개별 승인
- 선택: **노드 전체(2대 × 6코어) 안에서 파드 한도·replicas·배치를 자유롭게 조정** (사용자 선택)
- 적용 원칙: 코드 개선과 자원 조정의 효과를 구분하도록 한 번에 하나만 바꾸고, 변경마다 이 문서에 근거와 전후 수치를 남긴다.

### D1 적용 세부 (2026-09-26)

- 대시보드 UID는 `price-throughput-load-test`이다. Grafana API로 생성했다.
- JSON 위치: Manifest 레포의 `monitoring/`은 서비스 Argo CD 애플리케이션이 추적하는지 레포만으로 확인할 수 없었다. 그래서 대시보드 JSON이 매니페스트로 해석될 위험을 피해 **루트 `dashboards/`**에 두었다(사용자 선택. 검토안: 모놀리식 작업 문서 폴더 / Manifest 루트 `dashboards/` / Argo 설정 먼저 확인).
- 패널 구성: ① 부하(목표 대비 발행) ② 모놀리식 실행기·5xx ③ Redis 명령 처리량·상위 명령·지연·증폭률 ④ 워커 소비·반영 지연·미반영 ⑤ 리스너 전달·지연 ⑥ 파드·노드 CPU, 재시작
- 중단 기준 중 "Redis 명령 지연 p99"는 exporter가 명령별 평균 지연만 제공한다. 그래서 워커 쪽 Redis 명령 지연 히스토그램(`profit_worker_redis_command_duration_seconds`) p99로 판정한다.
