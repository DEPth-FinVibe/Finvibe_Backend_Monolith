# 제한된 운영 자원에서 실시간 시세 처리량 한계 끌어올리기

## 연결 Issue

- Issue: [#17 feat: 제한된 운영 자원에서 실시간 시세 처리량 한계 끌어올리기](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/17)

## 배경과 목표

- 실시간 시세는 모놀리식 → Redis Pub/Sub → WebSocket 리스너(현재가)와 모놀리식 → Kafka → 수익률 워커 → Redis(수익률)로 흐른다.
- 목표: 운영의 제한된 자원(노드 2대 × 6코어) 안에서 시세 부하를 단계적으로 올리며 병목을 찾고 개선해, 처리 가능한 최대 시세 처리량을 끌어올린다.
- 도달 목표 부하: 보유 종목 7,384개 × 초당 5회 ≈ **초당 약 37,000건**. 달성 여부와 무관하게 단계별 한계와 개선 근거를 기록한다.

## 현재 구현과 확인된 사실 (2026-09-26 00:45, mock 초당 100건 기준)

- **부하 발생기:** mock 프로바이더(`MockMarketDataStreamAdapter`)는 1초마다 구독 종목 중 무작위 N개(`stocks-per-tick`)를 골라 발행 스레드 4개로 Spring 이벤트를 보낸다.
- **모놀리식 경로:**
  - 분봉 집계는 동기로 처리한다(mock 스레드에서 실행).
  - `priceEventExecutor`(8~16스레드, 큐 1000)가 현재가 Lua 저장 → Pub/Sub → Kafka를 처리한다.
  - `reservationEventExecutor`(4~8스레드, 큐 500)가 예약 주문을 확인한다.
  - 두 실행기 모두 큐가 차면 호출 스레드가 직접 처리한다(CallerRuns).
- **자원 사용량:**

| 구성요소 | 사용량 | 한도 |
|---|---|---|
| 모놀리식 CPU | 0.57코어 | 0.7코어 (81%) |
| Redis 명령 | 초당 약 6천(유휴) → 약 22만 | — |
| Redis 마스터 CPU | 약 0.46코어 | 1코어 |
| 워커 CPU | 합계 1.0코어 | 2코어 × 2 |
| 리스너 CPU | 0.05코어 × 3 | 2코어 × 3 |
| Kafka 브로커 CPU | 약 0.1코어 | — |
| 노드 `5.104.82.70` | CPU 84% | 6코어 |

- Redis 상위 명령은 `HSET` 7.3만, `HGET` 4.9만, `HMGET` 2.4만, `GET`·`SET` 각 1.7만(초당)이다. 워커의 종목 → 보유 포트폴리오 팬아웃이 시세 1건을 Redis 명령 약 1,500~2,200개로 증폭하는 것으로 보인다.
- 모놀리식 기동은 약 290~350초가 걸린다. 설정을 바꿀 때마다 재기동 약 6분과 구독 재구축 약 5분이 추가로 든다.

## 해결해야 하는 문제

- P1. 단계별 처리량과 자원 사용량을 한 화면에서 비교할 측정 체계(대시보드·부하 단계 기록)가 없다.
- P2. 부하 발생기(mock)가 모놀리식 CPU(0.7)와 동기 Redis 왕복에 묶여, 파이프라인보다 먼저 한계에 닿을 수 있다.
- P3. 워커 팬아웃의 Redis 명령 증폭이 1순위 병목 후보다.
- P4. 모놀리식 시세 경로(CPU 한도, 동기 분봉 집계, 실행기 CallerRuns)가 2순위 병목 후보다.
- P5. 파드가 노드 한 대에 몰려 노드 CPU가 먼저 포화될 수 있다.

## 변경 범위

- 측정: 부하 단계별 지표 대시보드와 기록 절차
- 부하 발생기: mock 발행 구조 개선(필요 시 모놀리식 경로와 분리)
- 수익률 워커: Redis 명령 증폭 축소(배치·파이프라인·자료구조 등, 방식은 plan에서 결정)
- 모놀리식 시세 경로: 병목으로 확인되는 부분만 개선
- WebSocket 리스너: 병목으로 확인될 때만 개선
- 배포 설정: CPU·메모리 한도, replicas, 파드 배치(노드 전체 자원 안에서)

## 제외 범위

- 노드 추가·증설 등 하드웨어 확장
- KIS 실제 시세 경로의 구독 한도(82종목)
- MariaDB·Batch 경로
- 운영 사용자 데이터 정리(mock 가격으로 덮인 평가액은 KIS 복구 후 다음 개장 틱으로 갱신)

## 진행 방식

- 부하를 단계적으로 올린다(예: 100 → 250 → 500 → 1천 → 2.5천 → 5천 → …). 각 단계에서 5분 이상 유지하며 처리량, 지연(p50/p99), 자원 사용량을 기록한다.
- 첫 병목을 지표로 확정한 뒤 가설 → 개선 → 같은 단계 재측정으로 효과를 확인하고, 다음 단계로 넘어간다.
- 중단 기준(안): Redis 명령 지연 p99가 급증하거나, 모놀리식·리스너 에러율이 오르거나, 노드 CPU가 95%를 넘으면 즉시 이전 단계로 되돌린다.

## 예상 위험과 제약

- 운영 Redis Cluster와 Kafka를 모든 기능이 공유한다. 포화되면 로그인·주문 등 다른 기능도 느려진다. 실사용자는 없다고 확인받았다.
- mock 가격이 실제 사용자 평가액을 덮는다(이미 진행 중).
- 설정을 바꿀 때마다 모놀리식 재기동이 약 6분 걸려 반복 속도가 느리다.
- 대상 레포: monolith, Finvibe_Profit_Worker_Golang, websocket-listener, Finvibe_Backend_Manifest.
- Issue #16의 남은 작업(S6)과는 독립적으로 진행한다.
