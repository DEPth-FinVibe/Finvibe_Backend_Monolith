# 제한된 운영 자원에서 실시간 시세 처리량 한계 끌어올리기 — 결과 (현재가 경로)

- GitHub Issue: [#17](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/17)
- 기간: 2026-09-26 ~ 2026-09-27
- 범위: 현재가 경로(모놀리식 → Redis → WebSocket 리스너 → 브라우저). 수익률 경로(Kafka → 워커)는 다음 단계에서 다룬다.
- 상세 근거와 결정 기록: `03-decisions.md` (D1~D24)

## 요약

| 항목 | 시작 | 결과 |
|---|---|---|
| 처리량(전 구간, 초당 틱) | 약 220 (모놀리식 0.7코어) | **약 13,900** (약 63배) |
| 틱당 모놀리식 CPU | 약 3ms | **약 0.06ms** (모놀리식 0.83코어 ÷ 13,906/s) |
| 틱 손실 | 리스너에서 합치기로 버림(최대 초당 9,621건) | **0 (전 구간 무손실)** |
| 모놀리식 CPU 한도 | 0.7코어 | 2코어 (실사용 0.83) |

- 원칙: **틱을 버리지 않는다.** 종목별 합치기(coalescing)는 쓰지 않는다. 여러 틱을 한 번의 왕복·메시지로 묶어 보내기(batching)만 쓴다.
- 부하: 운영 클러스터(노드 2대 × 6코어)에서 mock 프로바이더로 7,384종목에 시세를 넣었다. 동시에 k6 웹소켓 게스트 1,000세션(세션당 20종목 구독)을 붙였다.

## 병목과 근거

1. **전체 키 SCAN(D12)**: 활성 노드 수를 세려고 약 205만 키를 5초·20초마다 훑었다.
   - 고치기 전: 기동 3~8분, Redis `SCAN` 초당 1,525개, 유휴 CPU 0.60코어, 스로틀링 38%
   - 고친 뒤: 기동 131초, `SCAN` 0, 유휴 CPU 0.29코어, 스로틀링 3.4%
2. **Redisson이 기본 Redis 연결을 가로챔(D13·D14)**:
   - JFR에서 `redisson-netty` 입출력 스레드가 CPU의 29.6%였다.
   - 원인은 `redisson-spring-boot-starter` 자동 설정이 `RedisConnectionFactory`를 Redisson으로 바꾼 것이다. 그래서 일반 명령까지 락용 클라이언트를 거쳤다.
3. **틱마다 동기 왕복 4회**:
   - Spring 이벤트 → `@Async` 실행기 2개 → Redis 동기 왕복(저장 1, 발행 1, 예약 조회 2) 구조였다.
   - Redis 서버 처리는 0.23ms인데, 클라이언트에서는 2.9ms를 기다렸다.
   - 예약 스레드 8개 ÷ (2회 × 2.9ms) ≈ 1,380/s로, 실측 한계와 같았다.
4. **예약 확인이 틱마다 Redis 조회(D18)**:
   - 예약이 없는 종목도 매번 2번 조회했다.
   - 종목별 "최고 매수·최저 매도 목표가"만 메모리에 두고, 넘을 때만 조회하도록 바꿨다.
   - 조회 대상을 찾던 `KEYS`는 마스터당 약 0.3초씩 Redis를 멈추게 했다.
5. **Serial GC(D21)**:
   - 메모리 1Gi, CPU 2 조건에서 JVM이 Serial GC와 힙 260MB를 골랐다.
   - 초당 1만 건에서 할당이 95MB/s가 됐고, 약 4초마다 전체 GC로 최대 0.83초 멈췄다(GC 시간 약 20%).
   - G1로 바꾼 뒤 정지 비율 1.3%, 최대 0.087초가 됐다.
6. **Lettuce 입출력 스레드 집중(D22·D23)**:
   - JFR에서 레인이 시간의 약 85%를 응답 대기로 보냈다.
   - 모든 인코딩·응답 처리가 `lettuce-nioEventLoop` 스레드 하나에 몰렸다(CPU 샘플 34%, 대부분 `String.charAt`).
   - 레인별 연결 4개로 나눠 20,000 목표에서 1.07만 → 1.40만/s가 됐다.
7. **리스너 합치기(D19·D24)**:
   - 리스너 입구에서 종목별 최신값만 남겨, 초당 9,621건(발행의 약 69%)을 버렸다.
   - 합치기를 없애고 세션별 대기열 + `events` 묶음 프레임으로 바꿨다. 드롭 0, 전달 2.9만 → 3.5만/s, 리스너 CPU -18%가 됐다.

## 종단간 전달 지연 (2026-09-27 15:09~15:14, 목표 10,000, k6 게스트 1,000세션)

- 지표: 리스너 `finvibe_ws_event_source_to_send_message_latency`. 틱이 만들어진 시각(ts)부터 세션 sendMessage 완료까지를 틱마다 잰다(리스너 `61b7803`).
- 결과: 처리 초당 9,333건(큐 쌓임 없음), **p50 124ms · p95 528ms · p99 1.28초**. 평소 p95는 0.25~0.35초이고, 15:11~15:13에 p95 1.3초로 한 번 튄 구간이 5분 값에 들어 있다.
- 목표 14,000(k6 연결 상태)에서는 실제 처리가 12,212/s에 그쳤다. 레인 큐가 1.7만까지 쌓여 p95가 4.4초였다. 이때의 지연은 처리 속도가 아니라 대기열 길이 때문이다. 그래서 "1.4만/s"(큐가 가득 찬 최대 처리량)와 종단간 지연은 같은 부하의 값으로 묶어 말하지 않는다.
- 참고: k6 세션이 없을 때 모놀리식은 목표 20,000에서 17,777/s를 처리했다(웹소켓 전달의 노드 CPU 경합이 없을 때).

## 최종 구조

```
KIS/mock ─▶ 종목 해시 레인 4개 (큐 2만, 최대 256건씩)
             ├─ 버전 Lua EVALSHA를 레인별 Lettuce 연결로 파이프라인 전송
             ├─ 채널별 틱 배열 1건으로 SPUBLISH
             └─ 메모리 예약 인덱스 비교 → 넘을 때만 Redis 조회·체결
Redis Cluster (마스터 3) ─▶ 리스너 3파드
             ├─ 메시지를 한 스레드에서 도착 순서대로 풀기
             ├─ 종목 해시 레인 8개로 모든 틱 브로드캐스트
             └─ 세션 대기열 → events 프레임(최대 256건)
                  └─ 쌓인 틱 2,000건 초과 또는 5초 무진전이면 끊고 재접속 시 스냅샷
```

## 검증

- 테스트:
  - 모놀리식 전체 통과. 레인 순서·드레인, 파이프라인 저장·NOSCRIPT 재시도, 예약 인덱스·마이그레이션, 예약 소비자 테스트가 새로 들어갔다.
  - 리스너 전체 통과. 무손실 순서, 묶음 프레임, 한도 초과 끊기, 레인 순서 테스트가 새로 들어갔다.
- 운영 측정: 단계마다 같은 부하(제어 키 `market:mock:control`)로 전후를 비교했다. 수치는 Prometheus 1~5분 평균이다.
- 프로파일링: JFR 두 번이다. 틱당 CPU 분포(D13), 스레드 대기 위치(D22).

## 남은 과제

- 모놀리식 노드 CPU 87%: 리스너·게이트웨이·Redis 마스터와 같은 노드라 경합한다(배치 분리 후보).
- 레인 한계 약 1.4만/s: 레인 스레드에서 바이트로 미리 인코딩하기, 틱당 할당(약 9.5KB) 줄이기가 후보다.
- 감시 종목 조회의 `KEYS`(`CurrentStockWatcherRepositoryImpl.findActiveStockIds`)
- D20 부하 발생기 분리: mock이 아직 모놀리식 안에 있다.
- `ActiveNodeRegistry` 레거시 노드별 heartbeat 키 제거, KIS 자격증명 쟁탈 대응
- 운영 복구: mock 끄고 KIS로 되돌리기, Kafka 시세 발행 다시 켜기
- 수익률 경로 부하 시험(Kafka → 워커)
