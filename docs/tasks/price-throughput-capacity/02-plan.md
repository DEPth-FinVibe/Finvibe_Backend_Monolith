# 제한된 운영 자원에서 실시간 시세 처리량 한계 끌어올리기 Plan

Overview와 GitHub Issue [#17](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/17)을 기준으로 진행 순서와 결정 포인트를 정의한다. 이 작업은 "측정 → 병목 확정 → 개선 → 재측정"을 반복한다. 그래서 개선 방식은 미리 정하지 않고, 병목이 확정될 때마다 결정 포인트(D5 이후)를 추가해 하나씩 확정한다.

## 완료 조건

- 부하 단계별 처리량·지연·자원 사용량을 한 화면에서 비교할 수 있다.
- 각 반복마다 "병목 근거 → 가설 → 변경 → 같은 부하에서 재측정" 기록이 `03-decisions.md`와 `04-result.md`에 남는다.
- 최종 도달 처리량과 그때의 한계 원인을 수치로 남긴다.
- 변경한 각 레포의 테스트가 통과한다.

## 추가로 확인한 사실

- 워커는 보유 포트폴리오마다 다음을 한다.
  - 읽기 3회: `GET` 수량, `HGET` scv, `GET` 레거시 평가액
  - 쓰기: `EVAL` 교체, `SET` 레거시 평가액, `HSET` 평가, `SADD` dirty
- 유저 총합은 유저의 포트폴리오 목록(`SMEMBERS`)과 각 포트폴리오를 다시 읽어 처음부터 합산한다.
- Kafka consumer lag 지표가 없다. 워커의 `profit_worker_price_apply_lag_seconds`(체결→반영 지연)로 대신 본다.
- 기존 대시보드: `Finvibe Profit Worker 관측 golang`, `Finvibe 웹소켓 리스너 메트릭`, `Redis Cluster`, `Finvibe KIS/Mock Subscription`, `Current Price & Redis Observability`

## 단계

### S1. 측정 체계와 기준선

- D1에 따라 단계별 비교 화면을 만든다.
- 각 단계에서 기록할 항목:
  - 목표 부하 대비 실제 발행량(mock `published`)
  - 모놀리식 실행기 큐와 CallerRuns 발생 여부
  - Redis 명령 수·CPU·명령 지연
  - 워커 반영 지연 p50/p99와 미반영 경과 시간
  - 리스너 팬아웃 지연
  - 파드·노드 CPU
- 초당 100건 기준선을 기록한다(Overview 수치).

### S2. 단계적 증량과 첫 병목 확정

### S3~Sn. 병목별 개선 반복

- 병목마다 결정 포인트를 추가해 선택지를 제시하고, 확정한 것만 구현한다.
- 같은 부하 단계에서 전후를 비교한 뒤 다음 단계로 증량한다.
- 현재 예상 후보(측정으로 확정 전):
  - 워커: 레거시 키 이중 쓰기 제거, 유저 총합 증분 갱신, 종목별 틱 합치기 창(coalescing), 포트폴리오별 쓰기 합치기
  - 모놀리식: CPU 한도, 동기 분봉 집계, 실행기 크기·거부 정책, mock 발행 구조
  - Redis: 샤드 간 부하 쏠림, 명령 파이프라이닝
  - 리스너: 팬아웃 합치기 설정
  - 배치: 파드 한도·replicas·노드 배치

## 결정 포인트

### D1. 단계별 측정 화면

1. **Grafana에 "시세 처리량 부하 시험" 통합 대시보드를 새로 만들고, JSON을 Manifest 레포에 커밋**
   - 장점: 단계별 전 구간을 한 화면에서 보고, 캡처를 포트폴리오에 바로 쓸 수 있다. 재현 가능하다.
   - 단점: 운영 Grafana에 대시보드가 하나 늘어난다.
2. **기존 대시보드 여러 개를 쓰고, 단계별 수치는 문서 표로 기록**
   - 장점: 추가 작업이 없다.
   - 단점: 화면이 흩어져 있어 단계 비교와 캡처가 번거롭다.
3. **Prometheus 쿼리 결과만 문서에 기록**
   - 장점: 가장 가볍다.
   - 단점: 시각 근거가 약하다.

AI 추천: 1번.

### D2. 부하 발생 방식

1. **모놀리식 mock을 유지하고, "목표 대비 실제 발행량"으로 발생기 한계를 따로 식별**
   - 장점: 실제 시세 진입점(모놀리식)이 파이프라인에 그대로 포함된다. 발생기 한계도 첫 병목 소재가 된다.
   - 단점: 모놀리식이 한계에 닿으면 그 뒤 단계에 부하를 더 걸 수 없어, 먼저 모놀리식을 개선해야 한다.
2. **별도 부하 발생 파드가 Redis·Kafka에 직접 발행(모놀리식 우회)**
   - 장점: 뒤 단계(워커·리스너)의 한계를 독립적으로 잴 수 있다.
   - 단점: 버전 부여 등 실제 진입 경로를 건너뛴다. 새 컴포넌트가 필요하다.
3. **1번으로 시작하고, 모놀리식이 병목이 된 뒤 뒤 단계 측정이 필요할 때만 2번을 추가**
   - 장점: 실제 경로를 우선하면서 막히면 우회한다.
   - 단점: 결정이 뒤로 미뤄진다.

AI 추천: 3번.

### D3. 증량 단계·유지 시간·중단 기준

- 단계(안, 초당 건수): 100 → 250 → 500 → 1,000 → 2,500 → 5,000 → 10,000 → 20,000 → 37,000
- 설정 방법: `EMITINTERVALMS=1000`에서 `STOCKSPERTICK`을 7,384까지 올린다. 그 이상은 간격을 줄인다(500ms → 200ms).
- 유지 시간: 단계마다 5분

선택지:
1. **위 단계표와 5분 유지, 중단 기준: Redis 명령 지연 p99 50ms 초과가 1분 지속 / 노드 CPU 95% 초과가 1분 지속 / 파드 재시작·OOM 발생 / 모놀리식 5xx 1% 초과**
   - 장점: 명확하고 보수적이다.
   - 단점: 단계가 많아 시간이 걸린다(설정마다 모놀리식 재기동 약 6분).
2. **단계를 절반으로(100 → 500 → 2,500 → 10,000 → 37,000), 기준은 같게**
   - 장점: 빠르다.
   - 단점: 병목 지점을 거칠게 잡는다.
3. **중단 기준 없이 끝까지 올려 무너지는 지점 확인**
   - 장점: 진짜 한계를 본다.
   - 단점: 운영 Redis·노드가 멈추면 복구에 시간이 든다.

AI 추천: 1번. 재기동 비용을 줄이기 위해, 모놀리식 재기동 없이 mock 설정을 바꿀 수 있는 방법(관리용 엔드포인트 등)을 S1에서 함께 검토한다.

### D4. 자원 재배치 허용 범위

1. **노드 전체(2대 × 6코어) 안에서 파드 한도·replicas·배치를 자유롭게 조정하고, 변경마다 결정 기록에 남김**
   - 장점: "제한된 자원을 최대한 활용"이라는 목표에 가장 맞다.
   - 단점: 시험과 무관한 파드(Batch, 모니터링 등)와 자원을 다툴 수 있다.
2. **자원 한도는 고정하고 코드 개선만**
   - 장점: 변수가 적어 개선 효과가 분명하다.
   - 단점: 모놀리식 0.7코어처럼 명백히 작은 한도도 그대로 둔다.
3. **한도 조정은 매번 개별 승인**
   - 장점: 통제가 쉽다.
   - 단점: 반복이 느려진다.

AI 추천: 1번. 코드 개선과 자원 조정의 효과를 구분하도록 한 번에 하나만 바꾼다.

## D16 이후: 초당 1만 건 이상을 위한 묶음 처리 재설계 (A안, 2026-09-26 사용자 선택)

### 목표와 원칙

- 목표: 현재가 경로를 같은 자원(모놀리식 한도 2코어, 리스너 3파드)에서 초당 1만 건 이상 처리한다.
- 원칙: **틱을 버리지 않는다.** 모든 틱을 버전 부여·저장·발행·예약 확인한다. 합치기(coalescing)가 아니라 여러 틱을 한 번의 왕복·메시지로 **묶어 보내기(batching)**다.
- 근거: 틱당 비용(모놀리식 CPU 약 1.1ms, Redis 동기 왕복 4회, 한 번에 약 2.9ms 대기)의 대부분이 "틱을 한 건씩 주고받는 비용"이다. Redis 서버의 실제 처리는 0.23ms 이내이고 CPU도 약 0.3코어다.

### 현재 구조 (코드 확인)

- 입구: `KisConnectionPool`(KIS)과 `MockMarketDataStreamAdapter`(mock)가 틱마다 Spring 이벤트 `CurrentPriceUpdatedEvent`를 발행한다.
- 이벤트 구독자 3개:
  - `KisMinuteCandleEventConsumer`: 분봉 집계를 동기로 처리한다(발행 스레드에서 실행).
  - `MarketEventConsumer.handlePriceUpdateEvent`: `@Async priceEventExecutor`에서 버전 Lua 저장 → SPUBLISH(JSON 1건) → Kafka(끔)
  - `MarketEventConsumer.handlePriceUpdateEventForReservation`: `@Async reservationEventExecutor`에서 `ZRANGEBYSCORE` 매수·매도 2회
- 리스너:
  - SPUBLISH 메시지 1건을 JSON 1건으로 파싱한다.
  - 종목별 최신값만 남기는 입구 합치기(`ingress_coalesced`)를 거친다.
  - 세션별로 토픽당 최신 작업만 남기는 출구 합치기(`outbound_coalesced`)를 거친다.
  - 웹소켓 프레임 1개에 틱 1건을 보낸다.
  - 현재 부하에서 합치기 발생은 초당 0.1건과 1.4건으로 거의 없다. 1만 건에서는 늘어날 수 있다.
- 프론트: `useMarketStore`가 `type: "event"` 메시지 1건씩 처리한다.

### 설계 구성요소 (각 항목의 선택지는 D17~D20에서 결정)

1. **수집 레인**:
   - 입구의 틱을 종목 해시로 나눈 소수의 전용 레인(스레드)에 넣는다. Spring 이벤트와 `@Async` 실행기 2개를 대신한다.
   - 같은 종목은 같은 레인이 처리하므로 순서가 유지된다.
   - 분봉 집계도 레인에서 처리한다.
2. **Redis 묶음 전송**:
   - 레인마다 짧은 창(예: 5ms) 또는 최대 건수(예: 256건)마다 모은다.
   - 버전 Lua(`EVALSHA`)를 틱마다 하나씩, 하지만 Lettuce 비동기 파이프라인으로 한 번에 보낸다.
   - 결과(버전 또는 오래된 틱)를 받은 뒤 발행 단계로 넘긴다.
3. **묶음 발행**: 샤드 채널마다 틱 배열을 메시지 하나로 SPUBLISH한다. 리스너는 배열을 풀어 모든 틱을 처리한다.
4. **메모리 예약 인덱스**:
   - 종목별 "최고 매수 목표가 / 최저 매도 목표가"만 메모리에 둔다. 틱 가격이 그 경계를 넘을 때만 Redis에서 실제 예약을 조회해 체결한다.
   - 예약 기능과 체결 의미는 그대로 유지한다.
5. **리스너 묶음 전송**: 세션마다 짧은 창 동안 쌓인 틱들을 웹소켓 프레임 하나(배열)로 보낸다. 프론트는 배열 메시지를 풀어 처리한다.
6. **부하 발생기 분리**: 1만 건 수준에서 모놀리식 CPU를 나눠 쓰지 않도록 발생기를 모놀리식 밖으로 뺀다.
