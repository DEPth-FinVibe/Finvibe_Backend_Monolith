# KIS 실시간 구독 용량 및 실패 처리 개선 Plan

## 기준 문서

- Overview: `docs/tasks/kis-realtime-subscription-capacity/01-overview.md`
- GitHub Issue: [#10](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/10)

## 추가 조사에서 확인된 사실

1. 운영 코드에서 `registerWatchingStock`, `renewWatchingStock`, `unregisterWatchingStock`을 호출하는 API 또는 메시지 경로가 없다. `loadtest` 초기화 외에는 watcher를 생성하는 호출자가 확인되지 않았다.
2. 활성 watcher의 Redis TTL은 10분이지만, 종목 단위 Set 전체 TTL을 갱신하므로 개별 사용자의 마지막 활동 시각을 기준으로 정렬할 수 없다.
3. 예약 종목은 현재가 이벤트로 예약 조건을 판정하므로 보유 종목보다 실시간 구독 필요성이 높다.
4. WebSocket에서 갱신되지 않은 현재가는 단건 내부 조회 시 Redis 캐시를 먼저 사용하고 캐시 miss에서 KIS REST 현재가 조회를 수행한다.
5. stale 현재가 REST 복구 스케줄러는 활성 watcher만 대상으로 하므로, 구독에서 제외된 전체 보유 종목을 자동으로 보완하지 않는다.
6. `getAvailableSessionCount()`는 pool에 등록된 세션 Map 크기를 반환하며, 실제 연결 상태와 남은 슬롯 수를 직접 표현하지 않는다.
7. 현재 `subscribe()`는 세션 부재를 정상 반환으로 처리하므로 스케줄러가 실제 실패를 성공으로 집계하고 소유권을 유지할 수 있다.

## 검증 가능한 완료 조건

1. 연결된 KIS WebSocket 세션이 0개면 종목 후보 조회, 종목별 분산 락 및 구독 호출을 수행하지 않고 다음 동기화 주기에 재시도한다.
2. 실제 활성 구독 수가 연결된 세션의 전체 용량을 초과하지 않는다.
3. 보유 종목이 7,384개여도 용량을 넘는 종목별 구독 호출과 오류 로그가 발생하지 않는다.
4. 사용자가 결정한 우선순위에 따라 높은 등급의 종목이 낮은 등급보다 먼저 용량을 배정받는다.
5. 동일 우선순위 종목이 용량을 초과할 때 결정된 정책으로 안정적으로 대상을 선정한다.
6. 실제로 성공하거나 이미 구독 중인 종목만 로컬 구독 순서와 분산 소유권을 유지한다.
7. 세션 부재, 용량 초과, 연결 끊김, 전송 실패가 명시적인 결과로 구분되고 각각 로그와 메트릭에 반영된다.
8. 연결이 끊기거나 Credential 할당에서 제외된 세션의 종목 매핑과 소유권이 다음 동기화 주기까지 정리된다.
9. 단일 노드와 다중 노드에서 각 노드가 자신의 실제 세션 용량만 사용하고 종목별 중복 소유를 만들지 않는다.
10. mock provider는 무제한 구독 동작을 유지하고 KIS 전용 용량 정책 때문에 제한되지 않는다.
11. 현재 외부 HTTP API, Redis 현재가 형식, 자산·포트폴리오 데이터와 Kafka event 계약을 변경하지 않는다.
12. 관련 단위 테스트와 전체 `./gradlew test`가 통과한다.

## 구현 단계와 검증 방법

### 1. 실시간 시세 port의 용량 및 구독 결과 계약 명시

- `MarketDataStreamPort`가 실제 연결 세션 수, 총 구독 용량과 남은 슬롯을 일관되게 제공하도록 계약을 보강한다.
- `subscribe()`가 성공 여부를 숨기지 않고 D3에서 결정한 결과 타입을 반환하도록 변경한다.
- KIS adapter는 이미 구독 중, 세션 부재, 용량 소진, 전송 실패와 신규 성공을 구분한다.
- mock adapter는 기존 무제한 구독 의미를 유지하면서 같은 port 계약을 구현한다.

검증:

- KIS connection pool 단위 테스트에서 연결 세션 0개, 세션 만석, 이미 구독 중, 전송 실패와 성공을 검증한다.
- 세션별 41개와 여러 세션의 합산 용량 및 남은 슬롯 계산을 검증한다.
- 실패 결과에서 심볼·종목 매핑이 남지 않는지 확인한다.

### 2. 세션 준비 상태 Gate 적용

- 동기화 주기 시작 시 Credential에 맞춰 세션을 동기화하고 닫힌 세션을 먼저 제거한다.
- 실제 연결 세션 용량이 0이면 D4 결정에 따라 종목 후보 조회와 소유권 획득 전에 종료한다.
- 비가용 상태 진입과 복구는 상태 전환 시 한 번만 INFO로 기록하고, 반복 주기는 저빈도 DEBUG 또는 메트릭으로 관찰한다.

검증:

- 세션 0개에서는 보유·예약·watcher repository, 종목 repository, 분산 락과 `subscribe()`가 호출되지 않는지 검증한다.
- 세션이 다음 주기에 복구되면 정상 동기화를 재개하는지 검증한다.
- 연결되지 않은 세션이 pool Map에 남아 있어도 가용 용량으로 계산하지 않는지 검증한다.

### 3. 우선순위 기반 용량 예산과 안정적인 후보 선정

- 예약, watcher와 보유 종목을 D1의 우선순위 tier로 분리한다.
- 중복 종목은 가장 높은 tier 하나에만 포함한다.
- 전체 후보를 먼저 합친 뒤 모든 보유 종목을 구독하는 현재 Phase 1 예외를 제거한다.
- 각 노드는 자신에게 연결된 세션 용량 안에서만 후보를 선정한다.
- 같은 tier가 남은 용량을 초과하면 D2 정책으로 선택하고, 낮은 tier 기존 구독은 높은 tier 신규 종목을 위해 해제한다.
- 심볼 조회는 실제 후보로 선택된 종목과 해제 대상에 한정해 7,384개 전체 조회 및 캐시 적재를 피한다.

검증:

- 예약·watcher·보유 종목 중복, tier별 용량 초과와 상위 tier 유입에 따른 하위 tier 교체를 검증한다.
- 보유 종목 7,384개와 세션 1개 조건에서 구독 시도가 최대 41개인지 검증한다.
- 입력 collection 순서가 달라도 D2에서 결정한 결과가 동일한지 검증한다.
- mock provider에서는 모든 후보를 계속 구독하는지 검증한다.

### 4. 실제 구독 결과와 분산 소유권의 원자적 정합성 확보

- 종목별 분산 락 안에서 소유권을 획득한 뒤 adapter 구독 결과를 확인한다.
- 신규 성공 또는 실제 기존 구독으로 확인된 경우에만 `subscriptionOrder`에 반영하고 소유권을 갱신한다.
- 세션 부재, 용량 소진과 전송 실패에서는 새로 획득한 소유권을 즉시 해제하고 로컬 순서에서 제거한다.
- 기존 소유 종목의 실제 세션 구독이 사라졌다면 재구독 결과에 따라 소유권을 유지하거나 해제한다.
- quota 밖, 비활성 또는 우선순위에서 밀린 종목은 WebSocket 해제와 소유권 해제를 함께 수행한다.

검증:

- 각 adapter 결과별 `subscriptionOrder`, `getSubscribedStockIds()`와 Redis 소유권 interaction을 검증한다.
- 실패 후 다음 주기에 잘못된 성공 상태가 남지 않는지 검증한다.
- 두 노드가 같은 종목을 동시에 처리해도 한 노드만 소유·구독하는지 검증한다.

### 5. Credential 락 인계 정책과 운영 관측 보강

- Credential 락 TTL과 갱신 주기는 D5 결정에 따른다.
- Credential 미할당, 세션 연결 중, 실제 연결 세션 0개, 총 용량, 활성 구독, tier별 선택·탈락과 adapter 실패 원인을 구분한다.
- 예상된 용량 초과는 종목별 ERROR가 아니라 동기화 주기별 집계 로그와 카운터로 기록한다.
- 기존 `kis.sessions.available`과 `kis.subscriptions.capacity`가 실제 연결 상태를 나타내도록 보정하거나 의미가 명확한 새 지표로 분리한다.

검증:

- `SimpleMeterRegistry`로 상태별 counter와 gauge 값을 검증한다.
- 7,384개 초과 조건에서 종목별 ERROR 로그 경로가 실행되지 않는지 코드와 테스트 interaction으로 확인한다.
- Credential 설정값과 로그에 app secret 또는 전체 app key가 노출되지 않는지 검토한다.

### 6. 전체 회귀 검증과 운영 확인 절차 작성

- connection pool과 synchronizer 단위 테스트부터 실행하고 전체 테스트로 확장한다.
- `04-result.md`에 배포 후 확인할 로그 순서와 actuator metric을 기록한다.
- 실제 운영 배포와 무중단 배포 작업은 수행하지 않고, 배포 후 검증 절차만 제공한다.

## 사용자 결정 포인트

Plan 승인 후 D1부터 한 번에 하나씩 A/B/C 선택을 확정하고 `03-decisions.md`에 기록한다. Plan 승인 자체는 어떤 선택도 확정하지 않는다.

### D1. 실시간 구독 tier 우선순위

A. 예약 종목 → 활성 watcher → 보유 종목 순으로 배정하고, 보유 종목은 남은 슬롯만 사용한다.
   - 장점: 예약 주문 판정을 먼저 보호하고 실제 활성 수요가 생기면 전체 보유 목록보다 우선할 수 있다.
   - 단점: 현재 운영에는 watcher 생성 경로가 없어 당장은 예약 다음에 일부 보유 종목이 채워진다.
B. 예약 종목 → 보유 종목 → 활성 watcher 순으로 배정한다.
   - 장점: 기존의 보유 종목 보호 의도를 가장 많이 유지한다.
   - 단점: 7,384개 보유 종목이 항상 용량을 소진해 향후 활성 watcher가 실시간 구독되지 못한다.
C. 예약 종목과 활성 watcher만 구독하고 보유 종목은 WebSocket 대상에서 완전히 제외한다.
   - 장점: 실시간 필요성이 명확한 대상에만 제한된 용량을 사용한다.
   - 단점: 현재 watcher 생성 경로가 없으므로 대부분의 보유 종목은 실시간 이벤트를 전혀 받지 못한다.

AI 추천: A. 거래 정확성과 활성 수요를 우선하면서도 현재 남는 슬롯을 보유 종목에 사용할 수 있어 기존 동작과의 단절이 가장 작다.

### D2. 같은 tier가 남은 용량을 초과할 때의 선정 정책

A. 현재 실제 구독 중인 종목을 먼저 유지하고, 남은 자리는 `stockId` 오름차순으로 안정적으로 채운다.
   - 장점: 입력 순서와 Redis `KEYS` 반환 순서에 영향받지 않고 불필요한 구독 churn을 최소화한다.
   - 단점: 동일 tier의 후순위 종목은 장중에 계속 선택되지 않을 수 있다.
B. 동기화 주기마다 초과 종목을 순환시켜 전체 종목을 시간 분할로 갱신한다.
   - 장점: 장기적으로 더 많은 종목이 한 번씩 실시간 가격을 받을 수 있다.
   - 단점: 5초마다 대량 구독·해제가 발생해 KIS 제한, 가격 공백과 운영 불안정 위험이 크다.
C. Redis에 종목별 최근 활동 시각을 저장하고 가장 최근에 사용된 종목을 우선한다.
   - 장점: 실제 사용자 수요에 가장 가까운 종목을 선택할 수 있다.
   - 단점: 현재 watcher 호출 경로와 개별 활동 시각이 없어 새 projection, 호출 경로 및 만료 정책까지 범위가 커진다.

AI 추천: A. 이번 장애의 핵심인 용량 초과와 반복 구독을 가장 작은 변경으로 안정화하며 결과가 결정적이다.

### D3. `subscribe()`의 성공·실패 계약

A. `SUBSCRIBED`, `ALREADY_SUBSCRIBED`, `NO_SESSION`, `NO_CAPACITY`, `SEND_FAILED`를 구분하는 명시적 결과 타입을 반환한다.
   - 장점: 스케줄러가 소유권 처리와 메트릭을 원인별로 정확히 결정할 수 있다.
   - 단점: port와 KIS·mock adapter, 테스트의 계약 변경 범위가 boolean보다 크다.
B. 성공 여부만 boolean으로 반환한다.
   - 장점: 변경이 단순하다.
   - 단점: 연결 장애, 용량 부족과 전송 실패를 구분하려면 adapter 내부 로그나 별도 상태 조회에 의존한다.
C. 예상된 세션 부재와 용량 초과도 예외로 전달한다.
   - 장점: 기존 `void` 계약에서 실패 전파를 빠르게 추가할 수 있다.
   - 단점: 정상적인 운영 backpressure까지 예외와 ERROR stack trace로 처리해 로그 소음과 제어 흐름 복잡도가 커진다.

AI 추천: A. 부분 장애를 원인별로 관측하고 실패를 성공으로 오인하지 않게 하는 목표에 가장 직접적이다.

### D4. 연결된 세션 용량이 0일 때의 동기화 동작

A. 해당 주기를 즉시 종료하고 5초 뒤 다음 스케줄에서 다시 세션 동기화부터 시도한다.
   - 장점: 7,384개 후보 조회, 분산 락과 종목별 오류를 만들지 않고 scheduler thread도 점유하지 않는다.
   - 단점: 연결이 수백 ms 뒤 완료돼도 다음 주기까지 최대 약 5초 더 기다린다.
B. scheduler thread에서 제한 시간 동안 세션 연결 완료를 기다린 뒤 같은 주기를 계속한다.
   - 장점: 연결이 빠르게 완료되면 다음 주기를 기다리지 않고 구독을 시작한다.
   - 단점: 비동기 연결을 동기 대기로 바꾸고 여러 scheduler 작업의 thread 점유 및 timeout 정책이 추가된다.
C. 현재처럼 후보를 처리하고 adapter가 종목별로 세션 부재를 거절하게 한다.
   - 장점: scheduler 흐름 변경이 작다.
   - 단점: 운영에서 확인된 대량 오류, 불필요한 분산 락과 실패 상태 오인의 원인을 유지한다.

AI 추천: A. 세션 준비 전 작업을 명확히 차단하고 기존 5초 동기화 주기로 자연스럽게 복구할 수 있다.

### D5. Credential Redis 락 인계 시간

A. 기본 TTL 60초와 갱신 주기 20초를 유지하고, 준비 중에는 D4 정책으로 안전하게 대기한다.
   - 장점: 일시적인 Redis·네트워크 지연에서 이전 노드와 새 노드가 같은 Credential을 중복 사용할 위험이 가장 낮다.
   - 단점: 비정상 종료 후 실시간 구독 복구가 최장 약 60초 늦어질 수 있다.
B. TTL을 30초, 갱신 주기를 10초로 줄인다.
   - 장점: 비정상 종료 후 Credential 재할당 시간이 절반 수준으로 짧아진다.
   - 단점: 30초 이상의 stop-the-world, Redis 장애 또는 네트워크 단절에서 살아 있는 노드의 락이 만료될 위험이 커진다.
C. 새 노드 시작 시 기존 Credential 락을 강제로 삭제하거나 탈취한다.
   - 장점: 재시작 직후 즉시 Credential을 얻을 수 있다.
   - 단점: 이전 노드가 실제로 살아 있으면 같은 Credential을 동시에 사용해 KIS 연결 충돌과 제한 위반이 발생한다.

AI 추천: A. 이번 범위에서는 구독 대량 실패를 차단하고 안전한 자동 복구를 우선하며, 무중단 배포와 공격적인 락 인계는 제외 범위로 유지한다.
