# README 아키텍처 중심 전면 개편 Plan

## 완료 조건

- `README.md`가 기존 내용을 보존하지 않고 새 구조로 전면 교체된다.
- 처음 보는 면접관이 첫 화면에서 Monolith의 핵심 책임과 주변 서비스와의 경계를 이해할 수 있다.
- GitHub에서 렌더링 가능한 Mermaid 다이어그램이 전체 요청·이벤트 흐름을 보여준다.
- Monolith, WebSocket Listener, Profit Worker, Manifest 저장소 링크가 유효하다.
- 각 서비스의 핵심 역할과 분리 이유가 간결하게 설명된다.
- 각 애플리케이션 서버의 수평 확장 방식과 제약이 실제 구현에 맞게 설명된다.
- Markdown 링크, Mermaid 문법과 문서 포맷이 검증된다.

## 구현 단계와 검증 방법

### 1. 면접관 관점의 README 정보 구조 확정

- 한 문장 소개: Monolith가 Finvibe의 핵심 비즈니스와 실시간 시장 이벤트의 중심임을 설명
- Monolith 중심 전체 아키텍처 다이어그램
- 관련 저장소와 이동 링크
- Monolith에 남긴 책임과 별도 서버로 분리한 책임
- Monolith의 핵심 책임: API, 도메인 트랜잭션, KIS 시세 수신, 상태 저장, 이벤트 발행
- 서버별 수평 확장 전략
- Monolith 내부 도메인 모듈
- 기술 스택 및 로컬 실행

검증: 사용자 결정과 확정된 목차를 대조한다.

### 2. 아키텍처 다이어그램 작성

- Monolith를 중앙에 두고 Client, KIS, Redis Cluster, Kafka, WebSocket Listener, Profit Worker, MariaDB의 관계를 표현한다.
- UI 시세 경로와 수익률 계산 경로를 색상과 라벨로 구분한다.
- Mermaid 노드와 별도의 저장소 표에서 관련 GitHub 저장소로 이동할 수 있게 한다.

검증: Mermaid CLI 또는 호환 렌더러로 문법을 검사하고 렌더링 결과를 확인한다.

### 3. 역할·분리 이유·스케일 아웃 설명 작성

- Monolith는 REST API, 도메인 규칙, 트랜잭션, KIS 시세 수신과 이벤트 발행을 책임지는 핵심 서버로 설명한다.
- WebSocket Listener는 장기 연결과 대규모 fan-out을 격리하는 서비스로 설명한다.
- Profit Worker는 Kafka 기반 비동기 수익률 계산과 Redis 갱신을 담당하는 서비스로 설명한다.
- 주변 서비스는 자체 설명보다 "Monolith에서 무엇을 덜어냈는가"를 중심으로 설명한다.
- 각 서버의 수평 확장 단위와 조정 메커니즘을 구분한다.

검증: 각 저장소 코드와 Kubernetes Manifest에 근거한 사실인지 다시 대조한다.

### 4. 문서 검증 및 결과 기록

- `git diff --check`로 공백 오류를 검사한다.
- Markdown 링크의 대상과 Mermaid 구문을 검사한다.
- 변경이 `README.md`와 작업 문서에만 한정되는지 확인한다.
- 검증 결과와 운영 영향을 `04-result.md`에 기록한다.

## 결정 포인트

### D1. README의 독자와 중심축

1. **면접관을 위한 Monolith 중심 구성 — 사용자 선택**
   - Monolith가 담당하는 핵심 비즈니스, 트랜잭션과 이벤트 허브 역할을 가장 먼저 설명한다.
   - 주변 서비스는 Monolith에서 분리한 책임과 그 이유를 이해시키는 용도로 소개한다.
2. 전체 백엔드 시스템 중심 구성
   - 모든 서비스를 같은 비중으로 소개한다.
   - 전체 조감에는 좋지만 이 저장소가 담당하는 역할이 약해질 수 있다.
3. 개발자 온보딩 중심 구성
   - 실행 방법, 설정과 세부 기술을 우선한다.
   - 개발 진입에는 좋지만 면접관이 핵심 설계를 빠르게 파악하기 어렵다.

결정: 사용자의 요청에 따라 **1번**을 적용한다.

### D2. 다이어그램 범위

1. **단일 전체 아키텍처 다이어그램 — 추천**
   - 요청 경로, Redis 시세 경로, Kafka 수익률 경로와 데이터 저장소를 한 화면에 표현한다.
   - 서비스 관계를 한눈에 이해하기 좋다.
2. 전체 구조와 스케일 아웃 구조를 두 개의 다이어그램으로 분리
   - 확장 메커니즘까지 시각적으로 자세히 표현할 수 있지만 README가 길어지고 내용이 중복된다.
3. Monolith → Listener, Monolith → Worker만 표현
   - 매우 단순하지만 실제 중간 매개체인 Redis와 Kafka의 의미가 약해진다.

추천: **1번**. 중간 인프라를 숨기지 않으면서도 다이어그램 수를 최소화한다.

### D3. 스케일 아웃 표현 방식

1. **설계 능력과 현재 배포 상태를 구분 — 추천**
   - 모든 애플리케이션 서버가 수평 확장 가능하도록 설계되었음을 강조한다.
   - 동시에 현재 Manifest는 Monolith 1 replica, Listener 3 replicas, Worker 3 replicas임을 별도 문장으로 명시한다.
   - 과장 없이 확장성을 어필할 수 있다.
2. 설계 능력만 강하게 강조
   - 메시지는 강하지만 현재 자동 확장이나 다중 replica 운영으로 오해될 수 있다.
3. 현재 replica 수만 설명
   - 사실은 명확하지만 설계상 확장 능력을 충분히 전달하지 못한다.

추천: **1번**. "스케일 아웃 가능한 형태"라는 요구를 정확하고 신뢰감 있게 전달한다.

### D4. 기존 README의 성능 개선 사례

1. **전부 제거 — 사용자 선택**
   - 새 README를 시스템 구조와 서비스 경계 중심으로 유지한다.
2. 핵심 수치만 짧게 유지
   - 기술적 성과를 보여줄 수 있지만 새 목적과 경쟁한다.
3. 본문에서 제거하고 상세 문서 링크만 유지
   - 접근성은 남지만 README의 링크와 섹션 수가 늘어난다.

결정: 사용자의 "기존에 있던 내용은 다 없어도 된다"는 지시에 따라 **1번**을 적용한다.

## 의존 관계와 적용 순서

1. D1에 따라 면접관 관점의 Monolith 중심 설명을 적용한다.
2. D2로 다이어그램 개수와 포함 요소를 확정한다.
3. 다이어그램 바로 다음에 저장소 링크를 배치하고, 서비스 분리 이유 다음에 Monolith의 상세 역할을 배치한다.
4. D3로 확장성 문구와 현재 배포 상태 표기 수준을 확정한다.
5. D4에 따라 기존 본문을 제거하고 새 README를 작성한다.
6. 렌더링과 링크를 검증한 뒤 결과 문서와 PR을 작성한다.
