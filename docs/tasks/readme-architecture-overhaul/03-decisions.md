# README 아키텍처 중심 전면 개편 Decisions

## D1. README의 독자와 중심축

### 검토한 선택지

1. 면접관을 위한 Monolith 중심 구성
2. 전체 백엔드 시스템 중심 구성
3. 개발자 온보딩 중심 구성

### 결정

- **선택: 1번**
- **결정 주체: 사용자**

### 선택 이유와 트레이드오프

처음 저장소를 보는 면접관이 Monolith가 맡는 핵심 비즈니스, 트랜잭션과 실시간 이벤트 허브 역할을 빠르게 이해하는 것이 가장 중요하다. 주변 서비스는 동일한 비중으로 나열하지 않고 Monolith에서 어떤 책임을 분리했는지 설명하는 문맥에서 소개한다. 세부 운영 정보와 개발자 온보딩 정보의 비중은 줄어든다.

## D2. 다이어그램 범위와 문서 순서

### 검토한 선택지

1. Redis와 Kafka를 포함한 단일 전체 아키텍처 다이어그램
2. 전체 구조와 스케일 아웃 구조를 두 개의 다이어그램으로 분리
3. 중간 인프라를 생략한 서비스 관계 다이어그램

### 결정

- **선택: 1번**
- **결정 주체: 승인된 추천안에 따라 AI가 선택**

문서 순서는 사용자 피드백에 따라 다음과 같이 확정한다.

1. 한 문장 소개
2. Monolith 중심 아키텍처 다이어그램
3. 관련 저장소 링크
4. 서비스 분리 이유
5. Monolith의 상세 책임
6. 수평 확장 전략
7. 내부 모듈과 실행 방법

### 선택 이유와 트레이드오프

Redis Pub/Sub과 Kafka를 숨기지 않아 각 분리 서비스의 연결 방식과 목적 차이를 한눈에 전달할 수 있다. 저장소 링크를 다이어그램 바로 다음에 배치해 관심 있는 구현으로 빠르게 이동할 수 있게 한다. 단일 다이어그램이므로 개별 확장 토폴로지의 시각적 상세는 본문 표로 보완한다.

## D3. 스케일 아웃 표현 방식

### 검토한 선택지

1. 설계상 수평 확장 능력과 현재 배포 상태를 구분
2. 수평 확장 능력만 강조
3. 현재 replica 수만 설명

### 결정

- **선택: 1번**
- **결정 주체: 승인된 추천안에 따라 AI가 선택**

### 선택 이유와 트레이드오프

모든 애플리케이션 서버가 수평 확장 가능하도록 설계되었다는 강점을 전달하면서도 현재 자동 확장 적용 여부나 replica 수를 과장하지 않는다. 현재 Manifest의 Monolith 1 replica, WebSocket Listener 3 replicas, Profit Worker 3 replicas를 설계 설명과 분리해서 명시한다. 숫자가 바뀌면 README가 오래될 수 있으므로 Manifest 저장소를 기준 문서로 연결한다.

## D4. 기존 README 내용 보존 여부

### 검토한 선택지

1. 기존 성능 개선 사례와 관측성 설명을 전부 제거
2. 핵심 수치만 요약해서 유지
3. 본문에서 제거하고 상세 문서 링크만 유지

### 결정

- **선택: 1번**
- **결정 주체: 사용자**

### 선택 이유와 트레이드오프

기존 내용을 보존하지 않아도 된다는 사용자 지시에 따라 README를 새 목적에 맞게 전면 교체한다. 성능 최적화 성과를 README에서 바로 볼 수 없게 되지만, 면접관이 시스템 구조와 이 저장소의 책임을 빠르게 이해하는 데 집중할 수 있다.
