# 시세 버전 기반 현재가·수익률 정합성 확보 Decisions

## D1. `priceVersion` 계산 방식

- 결정일: 2026-09-25
- 검토한 선택지: 인메모리 순번 / Redis Lua에서 순번 발급(키 유지) / Redis Lua에서 순번 발급(hash tag 키 이전) / Redis `INCR` 카운터
- 선택: **Redis Lua에서 순번 발급, 기존 키 이름 유지** (사용자 선택)

### 내용

- `priceVersion = KIS 체결시각(epoch 초) × 10^6 + 같은 초 안 순번`
- 순번은 현재가 저장과 같은 Lua 스크립트에서 발급한다.
  - 저장된 버전의 초보다 새 틱의 초가 크면 순번 0
  - 같은 초면 저장된 버전 + 1
- 발급한 버전을 저장 현재가 JSON과 Pub/Sub·Kafka 이벤트에 똑같이 싣는다.

### 이유

- 재시작하거나 구독 소유 노드가 바뀌어도 단조성이 유지된다.
- 버전에 시각 의미가 남아서 D8의 지연을 초 단위로 읽을 수 있다.
- 키 이름이 그대로라 리스너 스냅샷 경로(`CurrentPriceSnapshotRedisRepository`)에 영향이 없다.

### 정정 (구현 착수 중 확인)

- Plan D1에는 "현재가 키 두 개가 다른 slot이라 Lua로 묶으려면 키 이전이 필요하다"고 적었다. 하지만 실제 키는 이미 `market:current-price:{stock:<id>}`, `market:current-price-updated-at:{stock:<id>}` 형식의 hash tag를 쓰고 있어 같은 slot이다.
- 따라서 키 이름을 유지하면서 두 키와 버전 키 `market:current-price-version:{stock:<id>}`를 Lua 하나로 처리한다. 기존 SET 두 번(왕복 2회)은 Lua 1회로 줄어든다.
- 버전은 JSON을 파싱하지 않고 별도 버전 키로 비교한다. 저장 JSON은 Java가 직렬화한 객체 끝의 `}` 앞에 `,"priceVersion":<v>`를 붙여 완성한다. 가격(BigDecimal) 표현을 Lua `cjson`으로 다시 인코딩하지 않기 위해서다.
- Lua의 숫자는 double이다. 버전(약 1.8×10^15)은 2^53 미만이라 정확하다. 다만 문자열로 바꿀 때는 `tostring` 대신 `string.format('%.0f')`를 쓴다(지수 표기 방지).

## D2. 오래된 틱 처리

- 결정일: 2026-09-25
- 검토한 선택지: 저장·발행 안 함 / 버전 붙여 발행하고 하위가 버림 / stale 플래그 붙여 발행
- 선택: **저장·발행 안 함** (사용자 선택)
- 버전 키 보존 기간(D2-1): **7일** (사용자 선택. 검토안: 7일 / TTL 없음 / 현재가와 동일한 5분)

### 내용

- 새 틱의 체결시각(초)이 저장된 버전의 초보다 작으면, Lua는 아무것도 쓰지 않고 stale을 반환한다. 이때 모놀리식은 현재가 저장, Pub/Sub, Kafka를 모두 건너뛰고 카운터만 올린다.
- 같은 초는 stale이 아니다. 순번을 하나 올려 새 틱으로 처리한다.
- 버전 키 TTL은 7일이다. 틱마다 갱신되고, 주말·연휴가 지나도 단조성이 유지된다.

### 이유

- 오래된 값이 어느 경로에도 나가지 않으므로, 하위 소비자가 모두 올바르게 구현됐다는 전제에 기대지 않는다.
- 현재가 키(5분)와 달리 버전 키가 7일 남아 있어서, 틱이 뜸한 종목에서도 복구 틱이 더 새로운 값을 되돌리지 못한다.

## D3. 워커의 하위 호환 방식

- 결정일: 2026-09-25
- 검토한 선택지: 버전 유도 / 기존 `at` 비교와 버전 비교 병행 / 버전 필수
- 선택: **버전 유도** (사용자 선택)

### 내용

- 이벤트에 `priceVersion`이 없으면 `updatedAt(epoch 초) × 10^6`으로 유도한다.
- `stock:{id}:price-application`에 `ver`가 없으면 저장된 `at`으로 같은 식으로 유도한다. 커밋할 때 `ver`를 함께 기록한다.
- 컨슈머 배치 dedup과 서비스의 반영 여부 판정은 모두 버전 하나로 비교한다.

### 이유

- 비교 경로가 하나라서 테스트 조합이 늘지 않고, 모놀리식과 워커의 배포 순서에 무관하다.
- 구 형식 이벤트끼리의 같은 초 충돌은 기존처럼 건너뛴다. 동작이 기존보다 나빠지는 경우는 없다.

### 구현 중 확인한 주의점

- 모놀리식은 `updatedAt`을 오프셋 없는 KST `LocalDateTime`으로 보낸다. 워커는 이를 UTC로 해석한다(`model.LocalTime`). 저장된 `at`도 그렇게 해석된 값이다.
- 이 값을 그대로 epoch으로 바꾸면 유도 버전이 실제 버전보다 9시간 크다. 그러면 배포 후 새 버전 이벤트가 9시간 동안 모두 오래된 틱으로 버려진다.
- 그래서 유도할 때는 wall clock 값을 KST(고정 +09:00, 한국은 일광절약시간이 없음)로 다시 해석해 epoch 초를 구한다. 기존 `updatedAt` 해석(나이 지표 등)은 이 작업에서 바꾸지 않는다.

## D4. 포트폴리오 총합 근거의 저장 위치

- 결정일: 2026-09-25
- 검토한 선택지: `sv`(버전)만 원자 저장 / `sv`+`sp`(근거 가격) 저장 / 전역 `price-application` 버전 사용
- 선택: **`pf:{id}` 해시에 `sv:{stockId}`만 `scv:{stockId}` 교체와 같은 Lua에서 기록** (사용자 선택)

### 내용

- 가격 틱을 반영하는 `replaceStockCurrentValuesScript`가 `scv:{stockId}`와 `sv:{stockId}`를 함께 쓴다.
- 매매로 보유가 없어져 `scv`를 지우면 `sv`도 함께 지운다.
- 새로 매수한 종목은 가격 틱이 오기 전까지 `sv`가 없다. 이는 "시세 근거 없음(버전 0)"을 뜻한다.

### 이유와 새로 확인한 사실

- 매매 이벤트는 `scv`에 `수량 × 체결가`를 증감분으로 더한다(`cache.go`). 그래서 매매 직후의 `scv`는 "근거 가격 × 수량"이 아니라 이전 시세 평가액과 체결가가 섞인 값이다. 다음 가격 틱이 오면 `새 가격 × 수량`으로 덮어써진다.
- 따라서 근거 가격(`sp`)을 저장해 `수량 × (실시간가 − 근거가)`로 보정하면 매매 직후에 틀린다.
- 대신 종목 평가액을 통째로 바꾼다: `표시 총합 = 서버 총합 − scv_i + 수량_i × 실시간가_i`. 실시간 시세 버전이 `sv_i` 이상일 때만 바꾼다. 이렇게 하면 매매 직후에도 정확하고, 근거 가격을 저장할 필요가 없다.

### Plan 정정

- Plan의 S4 "`{stockId: (basisPrice, version)}` 저장"과 D6 1번 수식 "서버 총합 + Σ 수량 × (실시간가 − 근거가)"는 위 방식으로 대체한다. 조회 API는 종목별 `(scv, 수량, sv)`를 내려줘야 한다.

## D8. 반영 지연 지표 방식

- 결정일: 2026-09-25
- 검토한 선택지: 버전 기반 지연 + 주기 격차 / 버전 기반 지연만 / 주기 격차만
- 선택: **버전 기반 지연 + 주기 격차** (사용자 선택)
- 비교 범위(D8-1): **보유 종목 전체** (사용자 선택. 검토안: 모놀리식 버전 키가 있는 종목만 / 보유 종목 전체)
- 점검 간격(D8-2): **30초**, 환경변수로 조정 (사용자 선택. 검토안: 15초 / 30초 / 60초)

### 새로 확인한 사실

- 기존 이벤트 나이 지표(`profit_worker_event_age_seconds`)는 `time.Since(updatedAt)`으로 계산한다. 그런데 KIS 체결시각은 KST wall clock이고 워커는 이를 UTC로 읽는다. 그래서 나이가 약 −9시간이 되고, `RecordAge`는 `age >= 0`일 때만 기록하므로 실시간 틱의 나이를 조용히 버리고 있었다.
- 모놀리식은 가격이 바뀐 틱만 Kafka로 발행한다. 그래서 버전만 비교하면 가격이 그대로인 종목도 "뒤처짐"으로 잘못 잡힌다.

### 내용

1. 버전 기반 지연
   - 이벤트 나이를 버전(없으면 KST로 유도한 체결시각) 기준으로 계산해 기존 나이 지표를 바로잡는다.
   - 반영 커밋 시점에 `현재 − 버전의 체결시각`을 새 히스토그램으로 기록한다. KIS 체결부터 수익률 반영까지의 종단 지연이다.
2. 주기 격차
   - 워커가 30초마다 모놀리식이 관리하는 보유 종목 집합(`market:holding:stock-ids`)을 읽는다.
   - 종목마다 모놀리식 버전 키, 현재가, 워커 반영 상태를 pipeline으로 읽는다.
   - "뒤처짐"은 모놀리식 버전 > 반영 버전이면서 현재가 ≠ 반영 가격인 경우로 정의한다. 뒤처진 종목 수와 최대 격차(초)를 gauge로 노출한다.
   - 모놀리식 현재가 키(TTL 5분)가 없는 종목은 판정하지 않는다.

### 구현 세부 (AI 판단)

- 보유 종목 목록은 워커가 SCAN으로 모으지 않고, 모놀리식의 `HoldingStockRedisRepository`가 이미 관리하는 집합 키 하나를 읽는다. 클러스터 전체 SCAN을 피하기 위해서다.

## D5. 조회 API의 MariaDB fallback 시 근거 처리

- 결정일: 2026-09-25
- 검토한 선택지: 근거 null + 지연 표시 / Batch가 근거도 DB에 저장 / fallback 시 클라이언트가 전체 계산
- 선택: **근거 null + 지연 표시** (사용자 선택)
- 내용: PR #15의 항목별 fallback으로 MariaDB 값을 내리는 항목은 종목별 근거를 비운다. 클라이언트는 그 항목을 보정하지 않고 서버 값을 그대로 보여주되, `updatedAt`을 기준으로 지연을 표시한다.
- 이유: Batch 레포와 스키마를 바꾸지 않아 범위를 통제할 수 있다. Redis 장애 중의 어긋남은 표시로 알린다.
