# 시세 버전 기반 현재가·수익률 정합성 확보 Plan

Overview와 GitHub Issue [#16](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/16)을 기준으로 구현 순서와 결정 포인트를 정의한다. 조회 API는 [#14](https://github.com/DEPth-FinVibe/Finvibe_Backend_Monolith/issues/14)의 범위를 이 작업에서 함께 구현한다.

## 목표 산출물

- Monolith
  - 시세 수신 지점에서 종목별 `priceVersion` 부여, Pub/Sub·Kafka 이벤트에 포함
  - 수익률 조회 API(`GET /portfolios/valuations`, #14)와 종목별 계산 근거 응답
  - 현재가 조회 응답에 `priceVersion` 포함
- Golang 수익률 워커
  - 비교 기준을 `updatedAt`에서 `priceVersion`으로 교체(같은 초 충돌 누락 해결), 버전 없는 이벤트와 호환
  - 포트폴리오 총합에 종목별 근거 저장
  - 반영 지연 지표
- WebSocket Listener
  - 클라이언트 시세 메시지에 `priceVersion` 전달
- FE
  - 종목별 최신 시세를 버전 비교로 갱신
  - 서버 총합을 근거 기준으로 실시간 보정해 표시
  - 초기 진입·재연결 시 구독 후 스냅샷 병합
- 문서: 결정 기록, 결과, 배포 순서와 롤백

## 완료 조건

- 같은 틱의 Pub/Sub 메시지와 Kafka 이벤트가 같은 `priceVersion`을 가진다.
- 같은 초에 `100 → 101`로 이어진 두 틱을 워커가 모두 받아들이고, 최종 총합은 101 기준이다. 기존에는 `price_timestamp_conflict`로 101을 건너뛰었다.
- `priceVersion`이 없는 기존 형식 이벤트도 워커가 기존과 같게 처리한다. 모놀리식과 워커 중 어느 쪽을 먼저 배포해도 깨지지 않는다.
- 클라이언트 시세 메시지와 현재가 REST 응답에 `priceVersion`이 있다.
- 조회 API가 유저·포트폴리오 총합과 종목별 `(basisPrice, priceVersion)`을 반환한다.
- 클라이언트 표시 총합이 같은 화면의 종목 행 평가액 합계와 일치한다.
- 재연결 중 들어온 웹소켓 메시지와 스냅샷이 겹쳐도 버전이 낮은 값이 높은 값을 덮지 않는다.
- 반영 지연 지표가 Prometheus에 노출된다.
- 각 레포의 관련 테스트가 통과한다.

## 구현 단계

### S1. 시세 버전 부여 (monolith)

- `CurrentPriceService.stockPriceUpdated` 진입 시 `priceVersion`을 한 번 계산한다. 계산 방식은 D1, 복구 틱 처리는 D2에서 정한다.
- `CurrentPriceUpdatedEvent`, `StockPriceUpdatedEvent`, 저장 현재가(`CurrentPrice`)에 같은 값을 싣는다.
- 버전은 Lua·JS·Go에서 모두 정확히 비교할 수 있도록 2^53 미만의 단일 정수로 인코딩한다.

검증: 같은 초 연속 틱, 초 경계, 복구 틱 혼입, 두 이벤트의 버전 일치 단위 테스트.

### S2. 워커 버전 비교 (golang worker)

- `StockPriceUpdatedEvent`에 `priceVersion`(optional)을 추가한다.
- 컨슈머 배치 내 dedup(`handleStockMessages`)과 `UpdateProfitsByStockPriceChanges`의 비교를 `priceVersion` 기준으로 바꾼다.
- `stock:{id}:price-application`에 `ver`를 추가한다. 버전 없는 이벤트와 기존 키의 처리 방식은 D3에서 정한다.

검증: 같은 초 다른 가격 틱 반영, 역순 도착 차단, 버전 없는 이벤트, 기존 키만 있는 상태에서 첫 버전 이벤트, 실제 Kafka·Redis Cluster 통합 테스트.

### S3. 리스너 전달 (websocket-listener)

- `MarketEventBroadcaster`가 `priceVersion`을 `data`에 복사한다.

검증: 필드 유무 양쪽 직렬화 테스트.

### S4. 총합 근거 저장 (golang worker)

- 포트폴리오 총합이 어떤 종목의 어떤 버전 가격으로 계산됐는지 저장한다. 저장 위치와 원자성은 D4에서 정한다.
- Batch warm-up·write-back이 읽는 기존 필드(`pv`, `cv`, `pr`, `ac`, `ua`)는 바꾸지 않는다.

검증: 부분 적용 후 재시도에서 근거와 `scv`가 일치하는지, 매매 이벤트로 수량이 바뀐 뒤 근거가 유지되는지.

### S5. 반영 지연 지표 (golang worker, 필요 시 monolith)

- 수익률 반영이 시세보다 얼마나 뒤처졌는지 지표로 노출한다. 방식은 D8에서 정한다.

검증: 지표 이름·라벨 카디널리티 확인, 로컬 Prometheus scrape.

### S6. 조회 API와 클라이언트 보정 (monolith + FE)

- #14 범위로 `GET /portfolios/valuations`를 구현한다: Redis 우선, MariaDB 항목별 fallback.
- 응답에 종목별 근거를 포함한다. fallback 시 근거 처리는 D5에서 정한다.
- 현재가 REST 응답에 `priceVersion`을 추가한다.
- FE `useMarketStore`는 종목별로 버전이 더 클 때만 시세를 갱신한다.
- FE 총합 표시 방식은 D6, 스냅샷 병합 방식은 D7에서 정한다(리스너에 이미 구독 직후 스냅샷이 있다).

검증: API Redis hit·부분 miss·전체 miss·연결 실패 테스트, FE 병합 로직 단위 테스트, 브라우저에서 재연결 시나리오 확인.

## 결정 포인트

각 결정은 구현 직전에 하나씩 확정하고 `03-decisions.md`에 기록한다.

### D1. `priceVersion` 계산 방식

KIS 체결시각은 초 단위라, 같은 초 안의 틱을 구분할 순번이 필요하다. KIS 구독은 노드별 소유권으로 분산되고(#10), 운영 모놀리식은 현재 replicas 1이다.

1. **KIS 체결시각(초) × 10^6 + 인메모리 종목별 초 안 순번**
   - 장점: 추가 I/O가 없고 가장 단순하다.
   - 단점: 재시작하거나 소유 노드가 바뀌면 같은 초 안에서 순번이 0으로 돌아가 버전이 뒤집힐 수 있다(최대 1초 동안).
2. **체결시각 × 10^6 + 순번, 순번을 현재가 저장과 같은 Redis Lua에서 원자적으로 발급**
   - 장점: 재시작·노드 이동에도 단조성이 유지된다. 저장된 버전보다 낮은 틱을 같은 자리에서 걸러낼 수 있다. 현재 `upsertCurrentPrice`는 `market:current-price:{id}`와 `market:current-price-updated-at:{id}`에 SET을 두 번 한다. Lua 하나로 합치면 왕복이 오히려 줄어든다.
   - 단점: 운영 Redis는 Cluster다. 두 키가 다른 slot이라 Lua 하나로 묶으려면 hash tag 키로 이름을 바꿔야 한다. 이 키는 리스너(`CurrentPriceSnapshotRedisRepository`)도 읽으므로 키 이전 절차가 필요하다. 키 이름을 유지하려면 `market:current-price:{id}` 값(JSON) 하나에 버전을 넣고 Lua `cjson`으로 비교해야 한다. 저장 실패 시 발행 정책도 필요하다.
3. **종목별 Redis `INCR` 순수 카운터**
   - 장점: 구현이 가장 쉽고 전역 단조를 보장한다.
   - 단점: 틱마다 왕복이 하나 늘고, 버전에 시간 의미가 없어 D8의 지연 지표를 초 단위로 읽을 수 없다.

AI 추천: 2번. 추가 비용 없이 1번의 재시작·노드 이동 구멍을 막고, 버전에 시각 의미가 남는다.

### D2. 오래된 시세 복구 틱(분봉 `at`) 처리

`StaleCurrentPriceRecoveryService`는 분봉 시각으로 `stockPriceUpdated`를 호출한다. 이 시각은 실시간 틱보다 이를 수 있다.

1. **버전을 같은 규칙으로 계산하고, 저장된 버전보다 낮으면 발행하지 않는다**
   - 장점: 오래된 값이 어느 경로에도 나가지 않는다.
   - 단점: D1이 2번일 때만 저장 버전과 원자적으로 비교할 수 있다.
2. **버전을 붙여 그대로 발행하고 하위(워커·클라이언트)가 버린다**
   - 장점: 모놀리식 변경이 가장 적다.
   - 단점: 불필요한 메시지가 나가고, 하위 구현이 모두 올바르다는 전제에 기댄다.
3. **복구 틱은 별도 플래그를 달아 발행한다**
   - 장점: 관측과 디버깅이 쉽다.
   - 단점: 모든 소비자가 플래그를 해석해야 해서 계약이 늘어난다.

AI 추천: 1번(D1이 2번일 때). D1이 1번이면 2번.

### D3. 워커의 하위 호환 방식

1. **버전이 없으면 `updatedAt(초) × 10^6`으로 유도하고, 기존 `price-application`의 `at`도 같은 식으로 유도한다**
   - 장점: 비교 경로가 하나로 합쳐지고, 배포 순서에 무관하다.
   - 단점: 구 이벤트끼리의 같은 초 충돌은 여전히 구분할 수 없다(구 형식 한정이라 기존과 동일).
2. **버전 유무에 따라 기존 `at` 비교와 새 버전 비교를 둘 다 유지한다**
   - 장점: 기존 동작을 그대로 보존한다.
   - 단점: 두 경로가 섞일 때 판정이 복잡하고 테스트 조합이 늘어난다.
3. **버전 필수로 바꾸고 모놀리식을 먼저 배포한다**
   - 장점: 코드가 가장 단순하다.
   - 단점: 배포 순서에 의존하고, 토픽에 남은 구 이벤트와 DLT 재처리분이 버려진다.

AI 추천: 1번.

### D4. 포트폴리오 총합 근거의 저장 위치

워커는 종목 락 안에서 여러 포트폴리오의 `scv:{stockId}`를 교체하고, 마지막에 `price-application`을 커밋한다. 중간에 실패하면 일부 포트폴리오만 새 가격이 반영된 채로 재시도된다.

1. **`pf:{id}` 해시에 `sv:{stockId}`(버전)와 `sp:{stockId}`(가격)를 `scv` 교체와 같은 Lua에서 기록**
   - 장점: 포트폴리오마다 근거와 `scv`가 원자적으로 일치해 정확하다.
   - 단점: 해시 필드가 보유 종목 수만큼 늘고, 매도로 보유가 없어질 때 함께 지워야 한다.
2. **종목 전역의 `stock:{id}:price-application`을 근거로 사용**
   - 장점: 추가 쓰기가 없다.
   - 단점: 부분 적용 구간에는 실제 계산 가격과 다를 수 있어서, 이 작업이 막으려는 불일치를 그대로 남긴다.
3. **`scv / 수량`으로 가격만 역산하고 버전은 전역 값을 사용**
   - 장점: 저장 변경이 없다.
   - 단점: 버전이 부정확하고, 소수 수량에서 가격이 반올림된다.

AI 추천: 1번.

### D5. 조회 API의 MariaDB fallback 시 근거 처리

1. **fallback 항목은 근거를 `null`로 내리고, 클라이언트는 보정 없이 서버 값과 "지연" 표시를 보여준다**
   - 장점: Batch 변경이 없다.
   - 단점: Redis 장애 중에는 총합과 종목 행이 어긋나 보인다(표시로 알린다).
2. **Batch write-back이 근거도 MariaDB에 저장한다**
   - 장점: fallback 중에도 보정할 수 있다.
   - 단점: Batch 레포와 스키마 변경이 추가된다.
3. **fallback 시 클라이언트가 총합을 종목 행 합계로 전부 계산한다**
   - 장점: 서버 변경이 없다.
   - 단점: 실현손익 등 서버만 아는 값이 빠질 수 있다.

AI 추천: 1번. 장애 상황의 정확도보다 범위 통제가 우선이고, 어긋남은 표시로 알릴 수 있다.

### D6. FE 총합 표시 방식

1. **서버 총합 + Σ 수량 × (실시간가 − 근거가)로 보정** (실시간 버전이 근거 버전 이상일 때만)
   - 장점: 서버가 기준값으로 남고, 종목 행과 총합이 같은 가격 집합으로 계산된다.
   - 단점: 수량 정보가 응답에 필요하다.
2. **클라이언트가 보유 목록과 실시간가로 총합을 전부 계산하고, 서버 총합은 랭킹 등에만 사용**
   - 장점: 가장 단순하고 지연이 없다.
   - 단점: 서버와 계산식이 갈라지고, 워커 결과를 화면에서 쓰지 않게 된다.
3. **보정하지 않고 서버 총합을 그대로 표시하되, 버전이 다르면 "갱신 중" 표시**
   - 장점: 구현이 가장 작다.
   - 단점: 어긋남을 드러낼 뿐 없애지는 못한다.

AI 추천: 1번.

### D7. 초기 진입·재연결 스냅샷 방식

확인된 사실: 리스너는 이미 구독을 등록한 직후 `market:current-price:{id}`를 읽어 `initial: true` 스냅샷을 보낸다(`MarketQuoteWebSocketHandler.sendInitialPriceSnapshots`). 스냅샷은 저장된 `CurrentPrice` JSON을 그대로 복사하므로, S1에서 `CurrentPrice`에 `priceVersion`을 넣으면 스냅샷에도 실린다. 다만 구독 등록 뒤 스냅샷 전송 전에 팬아웃된 더 새로운 틱이 먼저 도착하면, 현재 FE는 늦게 온 오래된 스냅샷으로 덮어쓴다.

1. **기존 리스너 스냅샷을 유지하고, FE가 `initial` 여부와 무관하게 버전 비교로 병합**
   - 장점: 서버 추가 변경이 없고, 순서 역전을 FE의 단일 규칙으로 해결한다.
   - 단점: 스냅샷 키 TTL(5분)이 지나면 스냅샷이 없어서 첫 틱 전까지 값이 비어 있다(기존과 동일).
2. **1번 + 리스너가 스냅샷 전송 시 해당 세션에 이미 보낸 버전보다 낮으면 생략**
   - 장점: 불필요한 오래된 메시지가 줄어든다.
   - 단점: 리스너가 세션별로 종목 버전 상태를 들고 있어야 한다.
3. **1번 + TTL 만료 대비로 FE가 스냅샷이 없는 종목만 현재가 REST로 보충**
   - 장점: 장 마감 후처럼 틱이 없는 구간에도 값이 채워진다.
   - 단점: FE에 보충 로직과 요청이 추가된다.

AI 추천: 1번. 병합 규칙 하나로 순서 문제가 풀리고, TTL 만료는 이번 문제(경로 간 불일치)와 별개다.

### D8. 반영 지연 지표 방식

워커에는 이미 이벤트 나이(`RecordAge`: 현재 − `updatedAt`) 지표가 있다.

1. **기존 나이 지표를 유지하고, 워커가 커밋 시 "발행 버전 − 이전 반영 버전"의 초 단위 차이를 히스토그램으로 기록**
   - 장점: 종목 라벨이 없어 카디널리티가 낮다.
