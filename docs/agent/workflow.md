# AI 작업 절차

이 문서는 Finvibe Backend Monolith의 코드, 설정, 스키마, 인프라 또는 문서를 변경할 때 적용한다. 질문 답변과 읽기 전용 조사는 이 절차의 대상이 아니다.

## 대원칙

> 결정은 사용자가 한다. AI는 선택지와 추천 근거를 제시하고, 확정된 결정을 구현하고 검증한다.

- 사용자가 명시적으로 위임하지 않은 결정은 임의로 확정하지 않는다.
- 위임받아 결정한 내용도 `03-decisions.md`에 선택과 근거를 남긴다.
- 예외적으로 이 절차를 생략하거나 단축해야 한다면 구현 전에 사용자 확인을 받는다.
- 기존 작업 트리의 변경은 사용자 작업으로 간주하고 보존한다.
- 저장소를 변경하는 모든 작업은 승인된 Overview, GitHub Issue, 작업 브랜치와 PR을 가진다.

## 기록별 역할

| 기록 | 책임 |
|---|---|
| GitHub Issue | 운영 작업 등록, 문제·범위·완료 조건 추적 |
| `docs/tasks/<task-name>` | 상세 조사, plan, 사용자 결정과 최종 결과 보존 |
| Git commit | 결정과 독립적인 구현 단위의 변경 이력 |
| GitHub PR | 실제 diff, 검증 결과, 운영 영향과 리뷰 정보 제공 |

같은 내용을 전부 복제하지 않는다. Issue와 PR에는 운영 추적에 필요한 요약을 쓰고 상세 근거는 작업 문서로 연결한다.

## 작업별 산출물

변경 작업 하나당 다음 폴더를 만든다.

```text
docs/tasks/<task-name>/
├── 01-overview.md
├── 02-plan.md
├── 03-decisions.md
└── 04-result.md
```

`<task-name>`은 작업을 식별할 수 있는 짧은 kebab-case 이름을 사용한다.

### `01-overview.md`

- 연결된 GitHub Issue 번호와 URL
- 작업 배경과 실제 증상
- 현재 구현과 확인된 사실
- 해결해야 하는 문제
- 변경 범위와 제외 범위
- 예상되는 위험과 제약

### `02-plan.md`

- 검증 가능한 완료 조건
- 구현 단계와 단계별 검증 방법
- 사용자 결정이 필요한 항목
- 각 결정의 1·2·3번 선택지, 장단점, AI 추천과 추천 근거
- 의존 관계와 적용 순서

### `03-decisions.md`

- 결정 ID(`D1`, `D2`, ...)와 주제
- 검토한 선택지
- 사용자가 선택한 안 또는 위임에 따라 AI가 선택한 안
- 선택 이유와 감수한 트레이드오프
- 구현 중 새 사실로 결정이 바뀌었다면 정정 이력

### `04-result.md`

- 실제 변경 파일과 동작
- 결정 사항이 어떻게 반영됐는지
- 수행한 테스트와 결과
- 구현 중 확인된 새 사실
- 운영 영향과 롤백 방법
- 남은 한계, 미완료 사항과 후속 과제

계획을 그대로 옮겨 적지 않고 최종 코드와 검증 결과를 기준으로 작성한다.

## 단계와 Gate

각 단계는 사용자의 확인 없이 다음 단계로 넘어가지 않는다.

### 1단계: 읽기 전용 조사와 Overview 승인

1. 최신 `main`의 코드, 문서와 기존 Issue를 읽기 전용으로 조사한다.
2. Overview 임시 초안을 대화 또는 저장소 밖의 임시 파일로 작성한다.
3. 사용자에게 문제 정의, 범위, 제외 범위와 위험의 확인을 요청한다.
4. 사용자 승인 전에는 branch와 `docs/tasks/<task-name>`을 만들지 않는다.

### 2단계: Issue·브랜치·정식 Overview

1. 승인된 Overview를 요약해 단일 GitHub Issue Form으로 Issue를 생성한다.
2. Issue 번호를 확인한다.
3. 최신 `main`에서 `<type>/<issue-number>-<slug>` 브랜치를 만든다.
4. `docs/tasks/<task-name>/01-overview.md`를 만들고 Issue 번호와 URL을 기록한다.
5. `docs: <작업> overview` 형식으로 커밋한다.

Issue를 만들 권한이 없거나 GitHub 연결에 실패하면 branch나 구현을 먼저 만들지 않고 사용자에게 알린다.

### 3단계: Plan

1. 승인된 Overview와 Issue를 기준으로 `02-plan.md`를 작성한다.
2. 결정 포인트를 빠짐없이 분리하고 각 항목에 1·2·3번 대안을 제시한다.
3. 사용자에게 plan과 결정 포인트 목록의 확인을 요청한다.
4. 확인 후 `docs: <작업> 구현 계획` 형식으로 커밋한다.

### 4단계: Decisions and Implementation

1. 결정 포인트를 한 번에 몰아서 처리하지 않고 하나씩 확정한다.
2. 결정 즉시 `03-decisions.md`에 선택과 근거를 기록한다.
3. 해당 결정으로 범위가 확정된 구현만 진행한다.
4. 관련 테스트를 실행하고 결과를 확인한다.
5. 결정 또는 독립적인 하위 작업 하나가 끝날 때마다 작게 커밋한다.

아직 확정되지 않은 결정에 의존하는 구현을 앞질러 진행하지 않는다.

### 5단계: Result와 PR

1. 전체 구현과 검증이 끝난 뒤 `04-result.md`를 작성한다.
2. 계획과 달라진 부분, 실패한 시도, 운영 영향과 남은 한계를 기록한다.
3. 필요한 전체 테스트와 정적 검증을 실행한다.
4. `docs: <작업> result` 형식으로 최종 문서 커밋을 만든다.
5. 작업 브랜치를 원격에 push한다.
6. `.github/pull_request_template.md`의 모든 항목을 작성해 일반 PR을 생성한다.
7. PR의 base가 `main`인지, `Closes #<issue-number>`가 있는지, 작업 문서와 검증 결과가 연결됐는지 확인한다.
8. PR URL을 사용자에게 전달한다.

Draft PR은 사용하지 않는다. 에이전트의 기본 책임은 PR 생성과 전달에서 끝나며, 명시적인 추가 요청이 없으면 승인, 병합, PR 종료 또는 브랜치 삭제를 수행하지 않는다.

## Issue 작성 규칙

모든 변경 작업은 `.github/ISSUE_TEMPLATE/work.yml`을 사용한다.

필수 내용:

- 작업 유형
- 배경과 문제
- 목표
- 변경 범위와 제외 범위
- 검증 가능한 완료 조건
- 운영 영향과 위험
- 생성할 `docs/tasks/<task-name>` 경로

버그라면 재현 절차, 기대 동작, 실제 동작과 영향 범위도 작성한다. Issue 제목은 무엇을 바꾸는지 한 문장으로 식별할 수 있게 작성한다.

## PR 작성 규칙

모든 PR은 `.github/pull_request_template.md`의 단일 양식을 사용한다.

- 관련 Issue를 `Closes #<issue-number>`로 연결한다.
- 변경 목적, 주요 변경과 작업 문서 경로를 작성한다.
- 실제 실행한 테스트 명령과 결과를 작성한다.
- API, DB, Kafka, 설정, 배포, 성능과 보안 영향을 확인한다.
- 롤백 방법과 리뷰 집중 지점을 작성한다.
- 해당 없는 항목도 삭제하지 않고 `해당 없음`과 이유를 적는다.
- PR 제목은 `<type>: <한국어 요약>` 형식을 사용한다.

PR 본문의 내용은 실제 diff와 `04-result.md`를 기준으로 작성하며 계획을 완료 결과처럼 복사하지 않는다.

## 브랜치와 커밋

- 새 작업 브랜치는 Issue 생성 후 최신 `main`에서 만든다. 다른 feature 브랜치 위에서 새 작업 브랜치를 만들지 않는다.
- 브랜치 이름은 `<type>/<issue-number>-<slug>` 형식을 사용한다.
- type은 `feat`, `fix`, `refactor`, `infra`, `test`, `docs` 중 작업 성격에 맞는 값을 사용한다.
- 예: `refactor/42-common-boundary-cleanup`
- 현재 작업 트리가 깨끗하지 않다면 기존 변경을 임의로 이동하거나 삭제하지 않는다. 필요하면 별도 worktree를 사용한다.
- 하나의 큰 커밋보다 overview → plan → 결정별 구현 → result의 흐름이 커밋 목록에서 보이게 한다.
- 커밋 메시지는 한국어로 작성한다.
- 사용자가 요청하지 않은 인접 코드 정리와 리팩터링을 같은 커밋에 섞지 않는다.

## 시작 체크리스트

```text
[ ] 최신 main과 기존 Issue를 읽기 전용으로 조사
[ ] Overview 임시 초안 작성 → 사용자 승인
[ ] GitHub Issue 생성
[ ] 최신 main에서 <type>/<issue-number>-<slug> 브랜치 생성
[ ] docs/tasks/<task-name>/ 생성
[ ] 01-overview에 Issue 연결 → 커밋
[ ] 02-plan 작성 및 결정 포인트 분리 → 사용자 승인 → 커밋
[ ] 결정 하나씩 확정 → 03-decisions 기록 → 구현·검증 → 커밋
[ ] 04-result 작성 → 전체 검증 → 커밋
[ ] 브랜치 push → 일반 PR 생성
[ ] base=main, Closes #Issue, 작업 문서와 검증 결과 확인
[ ] PR URL 전달
```

## 금지 사항

1. 승인된 Overview와 Issue 없이 저장소 변경을 시작하지 않는다.
2. Overview와 Plan 확인 없이 구현으로 넘어가지 않는다.
3. 사용자가 위임하지 않은 결정 포인트를 임의로 확정하지 않는다.
4. 결정 이력을 남기지 않고 구현하지 않는다.
5. 여러 독립 결정을 하나의 큰 구현과 커밋으로 묶지 않는다.
6. 기존의 미커밋 변경을 삭제하거나 덮어쓰지 않는다.
7. 검증하지 않은 결과를 완료로 기록하지 않는다.
8. PR 없이 작업을 완료 처리하지 않는다.
9. 사용자 요청 없이 PR을 병합하거나 닫지 않는다.
