# AI 작업 절차

이 문서는 Finvibe Backend Monolith의 코드, 설정, 스키마, 인프라 또는 문서를 변경할 때 적용한다. 질문 답변과 읽기 전용 조사는 이 절차의 대상이 아니다.

## 대원칙

> 결정은 사용자가 한다. AI는 선택지와 추천 근거를 제시하고, 확정된 결정을 구현하고 검증한다.

- 사용자가 명시적으로 위임하지 않은 결정은 임의로 확정하지 않는다.
- 위임받아 결정한 내용도 `03-decisions.md`에 선택과 근거를 남긴다.
- 예외적으로 이 절차를 생략하거나 단축해야 한다면 구현 전에 사용자 확인을 받는다.
- 기존 작업 트리의 변경은 사용자 작업으로 간주하고 보존한다.

## 작업별 산출물

변경 작업 하나당 다음 폴더를 만든다.

```text
docs/tasks/<task-name>/
├── 01-overview.md
├── 02-plan.md
├── 03-decisions.md
└── 04-result.md
```

`<task-name>`은 작업을 식별할 수 있는 짧은 kebab-case 이름을 사용한다.

### `01-overview.md`

- 작업 배경과 실제 증상
- 현재 구현과 확인된 사실
- 해결해야 하는 문제
- 변경 범위와 제외 범위
- 예상되는 위험과 제약

### `02-plan.md`

- 검증 가능한 완료 조건
- 구현 단계와 단계별 검증 방법
- 사용자 결정이 필요한 항목
- 각 결정의 선택지, 장단점, AI 추천과 추천 근거
- 의존 관계와 적용 순서

### `03-decisions.md`

- 결정 ID(`D1`, `D2`, ...)와 주제
- 검토한 선택지
- 사용자가 선택한 안 또는 위임에 따라 AI가 선택한 안
- 선택 이유와 감수한 트레이드오프
- 구현 중 새 사실로 결정이 바뀌었다면 정정 이력

### `04-result.md`

- 실제 변경 파일과 동작
- 결정 사항이 어떻게 반영됐는지
- 수행한 테스트와 결과
- 구현 중 확인된 새 사실
- 남은 한계, 미완료 사항, 후속 과제

계획을 그대로 옮겨 적지 않고 최종 코드와 검증 결과를 기준으로 작성한다.

## 단계와 Gate

각 단계는 사용자의 확인 없이 다음 단계로 넘어가지 않는다.

### 1단계: Overview

1. 현재 코드와 문서를 읽기 전용으로 조사한다.
2. `01-overview.md`를 작성한다.
3. 사용자에게 범위와 문제 정의의 확인을 요청한다.
4. 확인 후 `docs: <작업> overview` 형식으로 커밋한다.

### 2단계: Plan

1. 확인된 overview를 기준으로 `02-plan.md`를 작성한다.
2. 결정 포인트를 빠짐없이 분리한다.
3. 사용자에게 plan과 결정 포인트 목록의 확인을 요청한다.
4. 확인 후 `docs: <작업> 구현 계획` 형식으로 커밋한다.

### 3단계: Decisions and Implementation

1. 결정 포인트를 한 번에 몰아서 처리하지 않고 하나씩 확정한다.
2. 결정 즉시 `03-decisions.md`에 선택과 근거를 기록한다.
3. 해당 결정으로 범위가 확정된 구현만 진행한다.
4. 관련 테스트를 실행하고 결과를 확인한다.
5. 결정 또는 독립적인 하위 작업 하나가 끝날 때마다 작게 커밋한다.

아직 확정되지 않은 결정에 의존하는 구현을 앞질러 진행하지 않는다.

### 4단계: Result

1. 전체 구현과 검증이 끝난 뒤 `04-result.md`를 작성한다.
2. 계획과 달라진 부분, 실패한 시도, 남은 한계를 숨기지 않고 기록한다.
3. 필요한 전체 테스트를 실행한다.
4. `docs: <작업> result` 형식으로 최종 문서 커밋을 만든다.

## 브랜치와 커밋

- 새 작업 브랜치는 최신 `main`에서 만든다. 다른 feature 브랜치 위에서 새 작업 브랜치를 만들지 않는다.
- 현재 작업 트리가 깨끗하지 않아 안전하게 분기할 수 없다면 기존 변경을 임의로 이동하거나 삭제하지 말고 사용자에게 알린다.
- 하나의 큰 커밋보다 overview → plan → 결정별 구현 → result의 흐름이 커밋 목록에서 보이게 한다.
- 커밋 메시지는 한국어로 작성한다.
- 사용자가 요청하지 않은 인접 코드 정리와 리팩터링을 같은 커밋에 섞지 않는다.

## 시작 체크리스트

```text
[ ] 현재 브랜치와 작업 트리 확인
[ ] 최신 main 기준 작업 브랜치 생성
[ ] docs/tasks/<task-name>/ 생성
[ ] 01-overview 작성 → 사용자 확인 → 커밋
[ ] 02-plan 작성 및 결정 포인트 분리 → 사용자 확인 → 커밋
[ ] 결정 하나씩 확정 → 03-decisions 기록 → 구현·검증 → 커밋
[ ] 04-result 작성 → 전체 검증 → 커밋
[ ] PR의 base가 main인지 확인
```

## 금지 사항

1. overview와 plan 확인 없이 구현으로 넘어가지 않는다.
2. 사용자가 위임하지 않은 결정 포인트를 임의로 확정하지 않는다.
3. 결정 이력을 남기지 않고 구현하지 않는다.
4. 여러 독립 결정을 하나의 큰 구현과 커밋으로 묶지 않는다.
5. 기존의 미커밋 변경을 삭제하거나 덮어쓰지 않는다.
6. 검증하지 않은 결과를 완료로 기록하지 않는다.
